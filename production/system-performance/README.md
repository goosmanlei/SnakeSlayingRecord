# 制作页面与实体大卡性能交付

本包对应 `task-20261006-0005`。范围、原始输入及全部验收标准见[任务说明](../../planning/system-performance-optimization-task.md)。本任务优化读取、传输、请求调度与缓存，不生成媒体、不改写作品，不发布隔离测试评论或采纳决定。正式运行版本、发布、推送与完成状态以主项目 `.codex-task` 账本及下文冻结发布包回执为准。

本轮形成了可发布的系统候选：常用 54 个路径条件各做两轮对照，所有已复现慢路径均超过预先固定的波动门槛，其他关键路径无同口径回退。常用路径候选 P75 最大 254.75 毫秒；冷重建仍可能需要约 0.4—1.9 秒。完整逐路径结果见[前后对照](results.md)，原始样本及其摘要见[证据清单](evidence/manifest.json)。本机清理已删除 17 个失效路径、21,549 个文件（22,811,961,154 字节为逻辑文件大小，不等于 APFS 实际回收空间），逐路径缺失回读通过；冻结快照和当前预览仍为复现／发布保留。正式切换后的结果另记本机发布回执，不把候选测量当成已部署的测量。

## 体验目标与边界

用户在执行中要求从存储／缓存中间件和架构上解决等待，并补充“主要内容通常在 300 毫秒内可用”。测量前把“通常”固定为每个常用路径及首访／重复条件的 P75（按下文固定算法计算的第三四分位数）不超过 300 毫秒。原任务要求的两轮中位降幅大于前后较大四分位距仍独立检查；快速路径检查同口径回退。

主计时包含准确正文及必要操作控件，终点再等待两帧绘制。图片实际完成和音视频可播放另行检查。首访指新文档／首次目标，不是操作系统、浏览器、服务端缓存全部清空。空缓存、重启和写后失效会重新计算，不能承诺所有冷读取都在 300 毫秒内。采用缓存后，数据一致性优先于保留旧缓存速度。

## 准确基线与复现方法

三个前置任务已经完成并纳入基线：1008 对应 `task-20261006-0002`，1009 对应 `task-20261006-0003`，1010 对应 `task-20261006-0004`。系统基线为 `bc31d7dc424ccec1328926cc034a67f4be579fcf`；故事基线及依赖祖先校验在本包证据中记录。系统候选由故事 `config/instance.json.review_desk_commit` 与[双仓交付引用](system-delivery.json)共同锁定。

原始快照通过 SQLite backup 取得，不直接复制正在写入的库文件。冻结库 213,671,936 字节，SHA-256 为 `ddd3eac77736337a976ee85606c0f2ba0c5c8b8ba2861eac9ec5e2558bce2362`，包含 8,685 个对象、13,898 份修订、285 条评论、314 条评论事件和 98,993 个素材内容节点。1,398 份媒体共 1,194,229,443 字节，各自保留原件摘要。基线、候选和写入验证使用独立副本；正式库不用于测试写入。

对照使用同一台 macOS arm64 机器、已连接 Chrome、1440×900 视口，按基线／候选／基线／候选执行，每轮每侧每个路径条件十个有效样本。两侧使用相同页面观察脚本和请求计时包装器；页面时间来自 `performance.now()`，不采用工具往返耗时。原生 Python 3.9.6、SQLite 3.51.0 的对照与正式 Docker Python 环境分开记录，不能把原生测量直接称为正式容器测量。

候选每轮启动前清空服务端缓存，使用未用过的隔离端口；不预热目标对象，不清除用户浏览器的全局缓存。每个新文档清理该隔离源的 localStorage／sessionStorage；同文档重访保留缓存。原版响应 `no-store`，候选带内容摘要的静态文件可缓存、媒体重新验证后复用，业务 API 仍为 `no-store`。两侧均保留操作系统文件缓存。第一次未命中及慢样本保留。

四分位数始终采用 Hyndman–Fan type 7：排序后位置 `(n−1)×q`，相邻值线性插值；四分位距为 P75−P25。每组十个样本只描述这次实验，不报告可信长期尾延迟。原始记录保留 URL 中的准确对象、修订、版本／候选、筛选条件、内容／控件指纹、请求与字节、服务端处理、浏览器 CPU／堆内存及媒体事件。

证据中的 `raw/*.jsonl.gz` 是原始 JSONL 的无损 gzip，`manifest.json` 同时保存压缩前后 SHA-256；按原文件名解压到隔离运行目录即可重新汇总。主矩阵的一条已解释浏览器环境失败会使 `--require-complete` 保持非零，不能为得到零退出码篡改原始记录。

复现从本任务保留的冻结快照建立独立副本，系统分别检出准确基线／候选；不要连接正式库。`scripts/performance_server.py` 选择隔离实例，`PYTHONPATH` 选择系统版本。通过已连接 Chrome 与 `scripts/performance_browser.mjs` 执行真实点击序列，禁止用接口循环代替页面时间。分别保留原始 JSONL 后执行：

```sh
python3 scripts/performance_report.py \
  --baseline .runtime/system-performance/baseline-round2.jsonl \
  --comparison .runtime/system-performance/comparison-delete-browser.jsonl \
  --server-log .runtime/system-performance/baseline-server.jsonl \
  --server-log .runtime/system-performance/candidate-server.jsonl \
  --output .runtime/system-performance/final-summary.json --round 2 --round 3 --require-complete
```

最终配对使用原始编号 2、3：完整基线第 2 轮 → DELETE 候选第 2 轮 → 新基线第 3 轮 → DELETE 候选第 3 轮。`baseline-round2.jsonl` 从原始记录逐字节提取 610 行，没有修改时间、身份或耗时。页面、数据、浏览器、探针和固定序列未变的原版样本复用依据在测量协议中记录。V1 原型和 WAL 原型各自保留，均不计入最终通过结论。诊断 SQL／展开次数时单独运行 `scripts/performance_projection_probe.py`，不与页面计时竞争资源。

## 读写链路和六个方向的取舍

权威链路为业务 SQLite 与原件 → 一致读取事务 → 按准确身份组装当前动作数据 → 编号与 JSON 传输表示 → 页面正文／控件；原件通过同一文件句柄核对字节后分块发送。前台评论、采纳、参考选定及后台导入／发布仍先写权威事务，再由下一次读取反映。

| 方向 | 证据、采用范围与取舍 |
| --- | --- |
| 按需加载、目录与正文分离 | 启动曾等待无关模块与完整配置。采用资料／剧本元数据目录、进入配置页再取图标候选；制作拆解只读取所需素材元数据，镜头制作仍保留视频历史／参考正文。同一准确集内已知场镜复用目录，刷新及未知历史重新核对。 |
| 列表读取与数据库分页 | 原版素材诊断单次约 80,952 条 SQL、37,369 次记录展开。采用请求内元数据复用、独立可重建列表投影及 compact 列表响应；当前页仍按既有分组规则显示最多 40 项。原版本地翻页已是几十毫秒，保留本地分组分页；本轮没有新增业务摘要表和数据库分页维护链路。全量列表、分组总数及组合筛选仍核对。 |
| 媒体与 API 调度 | 原版为单线程，共享 Store；采用 4 个固定工作线程、8 个排队连接、独立数据库连接和启动一次迁移，媒体不占用业务读取事务。原件需保持哈希、归档引用与 Range 语义，本轮保留经核验的 Python 文件路径，没有新增 Nginx 静态映射或物化副本。 |
| 准确修订、编号及跨请求缓存 | 请求内复用不能消除重访时重复组装。采用事务失效的跨请求投影和成功响应字节缓存；编号也受准确事务代号保护。完整 JSON 图编码消除完全相同的嵌套字段，解码恢复独立树，不合并不同修订／版本／候选。 |
| 浏览器缓存、缩略图与按需媒体 | 原版静态文件和原件均不缓存。采用两个内容摘要资源包、gzip、ETag、媒体重新验证及原有按需媒体加载。大卡诊断正文从约 22 MB 降到约 270 KB 压缩表示，完整还原相等。原件不缩放、不降质；本轮不新增缩略图生产与清退体系。 |
| SQLite 与其他中间件 | 读取剖析主要为 Python 记录展开、重复关联和序列化；没有建立 PostgreSQL 所需的持续写争用／共享部署依据。WAL 原型经版本核验后放弃：正式 SQLite 3.46.1 的 Debian 补丁清单未包含 [SQLite 官方 WAL 页面](https://sqlite.org/wal.html)列出的 WAL-reset 修复；最终保留原有 DELETE，读快照会短暂阻挡写入提交，另测实际读写竞争。没有新增业务索引。Redis 7.2.16 的同正文回环读取实验未显示收益，不增加外部缓存服务、对象存储或费用。 |

Redis 比较每侧 30 次，使用持久连接、相同序列化正文和操作系统暖缓存：269,623 字节大卡缓存，SQLite 中位 0.0307 ms、Redis 0.3916 ms；368,324 字节场景缓存，分别 0.0387 ms／0.4530 ms。这只比较缓存正文读取，排除投影计算、压缩、失效和浏览器，不是页面提速比例。官方 Redis 发行包摘要及原始样本保留在 `evidence/architecture/middleware-comparison.json`，实验服务不部署到正式环境。

## 缓存一致性与资源边界

系统完整操作说明在审阅台仓库 `docs/production-performance.md`。本次缓存是可丢弃的派生数据，不是业务数据库替代品，也不是备份。

| 对象／层次 | 准确键与失效 | 容量、恢复与代价 |
| --- | --- | --- |
| 请求内修订、元数据、编号与关联 | 当前读取快照、对象和修订；请求结束清除 | 不跨请求共享可变对象；减少同一请求重复展开 |
| 素材列表、实体工作区和编号投影 | 实例数据库真实路径及文件身份、后端代码摘要、业务事务代号、准确参数、关系布局摘要 | 独立 `.runtime/read-cache.sqlite3`；成功完整重建后缓存；无缓存仍从权威记录正确读取 |
| 完整成功 API 字节 | 上述身份，加完整查询参数、视图、JSON／图表示和压缩协商 | 错误、冲突、未知结果及写响应不缓存；评论接口每次核对当前锚点 |
| 浏览器静态／媒体字节 | 静态文件内容 SHA-256；媒体同一打开文件的 SHA-256／ETag | 静态一年 immutable；媒体 private、no-cache；原件损坏报错，不能用旧缓存掩盖 |

业务库新增 `read_generations` 和每张业务表 INSERT／UPDATE／DELETE 触发器。实际写入与随机代号更新同事务提交，事务回滚时一起回滚。键取全部表代号，当前采用保守的整实例失效：评论、采纳／撤销、素材采用、参考选择、配置、作品／素材导入、增量发布都无需调用方另发失效消息。写入前已经开始的读请求保留它的快照；写入后的新请求使用新代号，前端选择序号防止迟到结果覆盖当前阅读。

磁盘有效条目最多 128 MiB／2,048 项，单项不超过 32 MiB，每连接 L1 不超过 16 MiB；4 个工作线程合计 L1 最多 64 MiB，另有启动连接。磁盘页数上限约 256 MiB，采用 DELETE 回滚日志及增量回收，提交后移除日志。逻辑缓存上限不等于进程总内存或缓存文件瞬时大小。跨进程相同请求用共享租约合并填充，异常退出最多 15 秒后可重建；期限用于恢复填充者，不决定数据新鲜度。

缓存锁忙、损坏、容量不足时回退权威读取；旧实例、旧代码、准确参数不同或代号已变的结果不可命中。全局失效简单且稳妥，但相关写入后的首次访问需要重新组装。这是本轮明确保留的成本，不能用命中率代替页面等待改善。

从故事任务 worktree 使用已有发布入口，系统 worktree 为 `../../linked-worktrees/task-20261006-0005/desk`：
