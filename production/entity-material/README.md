# 实体与素材大卡交付候选

本包交付统一业务编号、实体与状态读卡、关系图、素材版本与候选选择、准确引用和生成结果自检标题，并准备关系旧说明的受控清理。实现、数据修复和浏览器验收均使用本任务的故事／系统隔离工作区。正式删除、部署、集成和推送等待最终候选确认，尚未执行。

完整需求见 [任务说明](../../planning/entity-material-large-card-task.md)。六张输入原图保存在 [inputs/](inputs/)，真实尺寸、字节和 SHA-256 见 [输入清单](inputs.json)，未重编码。本包的技术验证不代表用户接受作品、素材或生成许可。

## 编号与准确身份

类型、前缀、唯一性范围和实际对象对应见 [编号表](codes.md)及 [完整映射](codes.json)。系统管理“编号前缀”页直接读取系统 `review_desk/business_codes.py` 的同一事实来源，没有手工改号流程。

对象编号按首次登记顺序全局唯一分配，既有对象按原登记时间／稳定身份一次分配；占号与映射一起导出，排序、刷新、筛选不重新编号。E／S／SH 现统一为全局唯一对象编号，正文集序与原始场内镜号只作位置追溯，686 项历史位置对应保留；资料、剧本与故事结构不显示简写编号。MV／MC 与卡片 V／C 保留素材内版本、版本内候选的局部序号，修改自检或关联不换号，评论编辑不换评论编号。准确规则及本轮变化见[两页与全剧参考重构](../breakdown-shot-v2/README.md)。

候选按钮严格为“候选N”，详情另显示 M／MV／MC。共享原件的旧独立素材身份与后来需求身份分别保留；大卡使用所选素材版本的编号，准确原件引用仍保留自己的身份。编号不替换底层对象 ID、修订、正文引用或采用记录。

## 数据结果及边界

[状态归属](states.json)覆盖 359 个状态：273 个完整状态（含 4 个退出当前制作的历史保留项），86 个旧片段。它们原先均有有效唯一实体引用，实际归属变更为 0。每项保留旧→新实体、依据及场景来源；本次修复展示与读取，历史状态仍能审阅。共享歌曲候选显示真实所属状态，关联阿蘅不推断为阿蘅整体形态，也不扩张当前认可范围。

阿蘅普通最新页面的原按钮并非禁用；查看较早素材方案时，前端把素材历史误判成整个实体历史，禁用了当前实体采纳。已修复该判断，在 `review` 隔离库完成采纳→取消→再次采纳。真正历史实体／状态仍只读；后端缺项、准确范围和生成准备校验保留。测试三次决定及两条评论没有进入干净 `delivery` 库或候选导出。

[引用清单](references.json)扫描全量关系修订来源和已生成候选的实际调用输入，按准确对象、修订、组成及范围去重：697 项，读取失败 0。STATE 253、EPISODE 167、ENTITY 141、ASSET 135、INPUT_LOCK 1；uses.index 保留调用次序。未发现不可恢复原件。本轮未复现用户原始网络“Failed to fetch”，不将推测写成其确定根因；实际修复遗漏的非媒体输入及正文来源路由，后端沿用已有的分号安全地址解析。真实浏览器打开历史状态、关系 E03/S005 正文、图像裁切、共享音色和准确音频范围，抵达原调用内容。

两条旧 WAV 调用终点与登记时长相差约 0.167 微秒，是 PCM 帧数与元数据舍入差。调用和原件不改；恢复沿用 [歌曲恢复工具](../../scripts/recover_song_publication.py)，只对既有两条记录按原件哈希／帧数核验视图，不放宽通用范围校验。

## 关系旧说明清理

**正式待删除为 34 个关系对象各一份旧修订说明，共 34 份。** 当前 157 个关系头及其事实不删。逐项影响见 [确认清单](history-review.md)与 [准确身份／哈希／依赖](relationship-history.json)。完整旧原文只为本次确认暂留在工作区 `.runtime/entity-material/relationship-before-review.json`，正式应用后按冻结哈希删除，不另存永久历史全文。

34 个旧修订的直接评论、入向依赖及其他修订 payload 引用均为 0；136 条出向依赖保留。全库 285 条评论及 314 个事件不变。8 个受管文件提及旧身份，是历史批次头／调用锁的元数据，没有旧说明正文副本；`production/entity-relationships.json` 的记录正文已是现说明，旧 expected_heads 只作追溯，字节无需改动。旧 Git 提交不重写。

仅清理旧 title／label／blocks，保留端点、方向、类型、依据、适用范围和原修订 ID。旧链接明确显示“说明已清理”，不返回最新原文冒充旧文。原散列证明原身份，事实散列证明清理边界，不能声称新字节仍等于旧 payload。若有原文评论，保留用户自身 quote 并明确旧文字锚点失效；独立合成测试验证此能力，本次没有这类直接评论。

[隔离清理](evidence/cleanup-isolated.json)及 [保全比较](evidence/preservation.json)证明只改 34 个 revision.payload，其他业务表和 1,396 个原件／受管文件哈希不变。新编号／清理凭据表不藏旧说明。单事务核对关系头、评论和 payload 哈希，冲突无部分删除；重复执行删除 0，未来写入自动清理刚被替代的说明。提交后截断 WAL、VACUUM，不只是隐藏选择器。

候选导出为 Schema 7，含编号及清理凭据。[导出→空实例恢复](evidence/export-restore.json)比较 28 张业务表一致，恢复不复活旧说明。清理后只用净化基线和新读者向前恢复，不回灌旧库。其他任务副本和既有 Git 提交保留其追溯边界，不拿它们恢复已清理说明。

## 确认后的串行操作和恢复

从本故事 worktree 执行。系统路径和候选见 [双仓计划](system-delivery.json)。确认前准备故事 `_prepare_integration --push`、系统最新 main 核对、镜像构建及只读预演。`.runtime/entity-material/release/` 冻结候选／目标头、镜像、三份摘要和唯一推送目标；不保存凭据。正式全库行散列与基线不符，包括新增评论，都停止并重新准备，绝不覆盖活库。

1. `scripts/entity_material_release.py apply` 带冻结 bundle、三个摘要及 `--apply`：发布锁→核对候选和旧服务→正式副本预演→系统受控 fast-forward→停旧读者→正式库再核对→单事务清理→WAL／VACUUM／校验→净化恢复基线→新镜像和不可变配置挂载→健康及源码验证。
2. 正式 3000 只做一次必要 Chrome 验收：EN002、ST092／自检、关系准确来源、旧说明提示、素材按钮、准确输入与编号说明。不在正式库新增测试采纳或评论，不重复开发全套回归。
3. 冻结包的 `publish-system` 推送唯一系统 upstream 并回读候选 SHA；只允许已确认的 fast-forward，远端移动即停。
4. `codex.project task _complete -g creative -p SnakeSlayingRecord --task task-20261005-0002 --note '完成标准与实际验证证据'` 受控集成故事 main、推送及回读。候选 `export/` 此时进入主目录；此前正式服务窗口的净化公开恢复基线在 `run/sanitized-recovery/export`。完成与故事推送以该回执为准。
5. 核对并停止预览进程，同包 `purge` 按冻结文件哈希、应用读者和专用挂载检查，删除本任务旧基线、测试库、清理前原文，以及已被净化恢复包替代的 `review`／`delivery` 过程目录。未知文件变化或读写占用即停；不删除系统 worktree，保留原件的正式／恢复副本、分支和必要回执。
