# 运行清理脚本独立复核

复核对象为 `scripts/asset_cleanup_runtime.py`、`tests/test_asset_cleanup_runtime.py` 及准确容器清单 SHA-256 `58f125142f3bb6514657555d29e6da4ede690e27afc3a326d8d4c8e111803168`。结论：已发现的归档中断恢复缺口完成修复，当前没有阻断此准确候选清理的代码问题。正式删除尚未执行，仍须用户确认统一候选与操作范围。

原问题出现在前一个容器已删除、后一个容器在创建归档目录后且保存归档回执前失败：重试同一 run 会因残留目录而拒绝，换 run 又无法承接此前删除的回执。修复将仅属于该 run、没有归档回执的部分目录精确改名并保留，登记 `interrupted_archives` 后重建归档；已归档或已删除项继续核验原回执，不以容器消失推定无条件成功。第二容器日志读取失败和归档半写中断的两条新增回归覆盖该问题。

独立检查覆盖：任务 worktree 边界、准确 manifest 哈希、全容器 ID/名称/命令/原挂载与执行状态、仅退出容器、失效来源仍不存在、原镜像仍存在、完整可写层 diff 未变化、每次删除前重新核对、私有日志和身份归档、回执哈希、`rm` 后未知结果恢复，以及整个余项集合在首个破坏操作前的预检。实际删除仅使用 `docker rm <完整ID>`，没有 force、停止进程、volume/image 删除或全局 prune；脚本不执行会创建失效挂载源的 `docker cp`。

独立运行 14 个测试全部通过，日志为 `runtime-cleanup-independent-tests.log`。真实预检回执另明确 `applied:false`，4 个精确候选均通过；15 个真实 Image SHA 无法重新读取的旧容器保留。模拟测试不代替真实删除效果验收，也不证明停止容器能恢复旧服务；正式运行依赖和当前服务仍由主协调者核对。
