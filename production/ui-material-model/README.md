# 导航与素材版本交付

本交付统一五个主页面的顶部子页导航、逐镜阅读和实体／素材卡片，并把素材版本的完整定义集中存储。历史记录保留原修订身份和内容，旧请求／回执按原始字节还原；镜头正文、媒体原件及已提交 Git 历史不重写。无需重新生成媒体。

[33项验收](acceptance.md)记录逐项结果；[独立审查](evidence/independent-review.md)记录发现和复验；[实际页面操作](evidence/browser-review.md)与截图单列，不能用自动检查代替。[候选检查汇总](evidence/verification.md)说明自动检查、原失败及补验范围。最终候选、确认和推送结果由项目任务账本及完成回执保存。

## 创作审阅

左侧仍为制作思路、故事创作、制作设定、全剧制作和系统管理五个入口。当前页面的子页在顶部同一行切换，链接、刷新和前进后退保持子页。未提交的文字与配置草稿按各自内容保存。

制作拆解按镜头独立排列：左侧读镜头设计，右侧查看该镜明确关联的素材。场头的归属按钮可多选，也可全部取消。镜头制作右侧只列视频，图片和声音参考在左侧准确输入区打开。列表不会因为素材属于本剧、本集或本场就推断该镜使用了它。

实体大卡依次显示基础信息、关系、状态列表和选定状态；状态素材另行分隔。双击关系实体打开新一层大卡，关闭后返回原卡的状态、版本、草稿和位置。素材先选版本，再选该版本的候选与原件／预览；未生成版本不显示其他版本的结果。多个状态可共享同一素材，切状态仍保留各自的候选与采用上下文。

集、场、镜的界面标签使用 E02、S003、SH004；正文和历史评论仍保留原文。历史链接保留原标识与准确修订，不能自动跳到最新结果。

## 数据包与旧记录读取

`migration.json` 是准确增量迁移包入口。完整内容定义与归档还原配方共用 `../../export/material-content.json`，包内只保存引用及校验值。映射包含原需求、共享素材、版本、候选和准确关联；缺少历史证据的字段保留缺口，不能补造模型、Prompt、输入或调用。

新的 Schema 6 导出集中保存内容、版本绑定和受管归档路径索引。恢复时重建旧逻辑记录及归档引用容器；读取接口还原准确原字节。兼容旧 Schema 1—5；没有完整定义绑定的旧实例不会冒充完整新格式。

故事脚本通过 `scripts/material_model_io.py` 读取受管 JSON。直接把引用容器当旧 JSON 解析会得到错误语义；需要原始请求或回执时，用系统的 `material_archives.read_bytes`，它会校验原始字节哈希。媒体原件仍按原路径和哈希读取。

## 确认前准备

全部命令在当前任务工作区执行。正式库、服务和两仓主分支在确认前保持原状；预演使用 `.runtime/ui-material-model/`。系统仓工作区为该目录下的 `system`，故事候选通过 `codex.project task _prepare_integration` 取得，并核对准备回执中的候选、原目标及后续推送目标。准备阶段不推送。

最终代码、数据包、说明和证据提交后，准备不可变发布包：

```bash
python3 scripts/ui_material_model_release.py prepare \
  --system-worktree .runtime/ui-material-model/system \
  --bundle .runtime/ui-material-model/release \
  --story-candidate "$STORY_CANDIDATE" --story-target "$STORY_TARGET" \
  --system-candidate "$SYSTEM_CANDIDATE" --system-target "$SYSTEM_TARGET"
python3 scripts/ui_material_model_release.py build --bundle .runtime/ui-material-model/release
python3 scripts/ui_material_model_release.py preflight --bundle .runtime/ui-material-model/release
```

上述四个变量取准备结果中的完整提交，不手填猜测值。`prepare` 固定双仓候选、迁移包、共享内容图、全部归档容器、旧镜像、挂载和部署配置；`build` 禁止拉取和构建期联网。`preflight` 通过只读 SQLite 备份校验当前正式库的准确头和增量前置条件，不初始化或写入正式库。

提交给用户审阅的内容包括两仓候选、`main / origin / refs/heads/main` 目标、三个发布包哈希、实际页面结果及以下切换顺序。准备成功不表示验收通过，也不表示获得发布确认。

## 明确确认后的串行交付

1. 按用户确认的三个哈希调用 `ui_material_model_release.py apply`。脚本核对候选、原目标、受管文件与发布包哈希，以及应用和代理服务身份；首次切换前再做只读备份预检。通过后受控集成系统候选，停止旧应用，再在单个事务内应用素材迁移增量。提交后用同一数据库连接执行 `PRAGMA wal_checkpoint(TRUNCATE)`，将已提交内容写回数据库并截断预写日志，避免日志继续保留去重前的全文；仅 `busy=0` 才继续校验并切换到新镜像与准确挂载，否则进入现有逆向恢复流程。发布回执的 `checkpoint` 保存检查结果。无关并发评论和业务对象保留；受影响素材头或索引冲突时整批拒绝。
2. 对正式页面做一次必要验收：五页入口、李寄共享音色版本2、未生成版本、关系弹窗和逐镜布局。运行回执写入发布包 `run/`，不修改已确认候选。候选与输入未变时不重复全部开发期回归。
3. 系统仓按确认目标推送 `origin main` 并回读远端完整提交。若远端发生分叉，停止交付，在任务工作区合并、补验并重新确认，不强推。
4. 执行 `codex.project task _complete -g creative -p SnakeSlayingRecord --task task-20261004-0009 --note '实际验收证据及发布回执'`，由任务系统受控集成故事候选、推送并回读。准确归档容器及公开导出在这一步随故事候选进入正式目录；之前的短暂窗口仍由新读取器兼容原始归档。不得提前执行此命令伪造确认。
5. 复用完成回执报告最终候选和推送结果，结束文件写入。不在完成后补写文档、追加提交或继续下一任务。保留工作区和分支，正常退出会话后才释放运行锁。

`apply` 的具体入口为：

```bash
python3 scripts/ui_material_model_release.py apply \
  --bundle .runtime/ui-material-model/release --apply \
  --manifest-sha256 "$SERVICE_MANIFEST_SHA256" \
  --image-receipt-sha256 "$IMAGE_RECEIPT_SHA256" \
  --model-manifest-sha256 "$MODEL_MANIFEST_SHA256"
```

哈希来自已展示并确认的不可变发布包。`--apply` 只是执行开关，不能替代用户确认。脚本本身不推送，也不执行任务完成命令。

## 恢复入口

故事主分支仍为已批准的原始目标提交时，使用同一发布包及同一三个哈希，把上面的 `apply` 改为 `recover`。恢复先校验交付文件、故事主分支、当前应用镜像及挂载、代理服务，再预检准确逆向增量；预检通过后停止应用，实际执行逆迁移并恢复旧服务。不会用隔离快照覆盖活库，也不会重置 Git。无关新增数据保留。

旧服务启动前，数据库须恢复为旧版本可读写的状态，包括处理新版本安装的触发器。逆迁移以 `require_legacy=True` 在同一事务内检查：若并发写入了本次迁移之外的新编码素材，旧版本无法读取，必须在逆向修改前整体拒绝，保留当前数据且不启动旧服务。首次切换若在数据库打开阶段失败，`apply` 仍先调用 `prepare_legacy_runtime` 检查并处理正式库；该步骤拒绝时不会启动旧服务。候选已准确运行时发生开库失败，则保留当前候选服务。

若本次涉及的素材、别名、定义或归档索引已有后续变动，逆向恢复会拒绝。显式 `recover` 的预检拒绝发生在停止应用之前；命令失败信息须另行保存，脚本不会自动生成恢复回执。`apply` 内的自动恢复失败才会在 `run/` 写入 `recovery-blocked-*`。实际逆迁移若在停机后失败，不会继续启动旧服务，应保留现场并基于当前库准备向前修复；不能加载旧读取器访问尚未恢复的新物理格式。

故事候选一旦进入故事主分支，即使 `_complete` 的后续推送失败，也不能再使用此恢复入口；须另建受控恢复任务，保持已提交归档、导出和数据库一致。不要单独运行旧的通用服务恢复命令绕过本任务的数据逆向检查。

公开包完整恢复到空实例的验证和原字节对照见验收表 D07—D09。恢复仅恢复数据与运行能力，不代表作品已被用户接受。
