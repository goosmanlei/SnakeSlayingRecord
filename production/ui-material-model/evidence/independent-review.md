## 原模型与数据历史的额外核对

旧版本签名只覆盖制作字段，独立修改素材用途、正文要求、规格、输出描述和输出检查时签名均不变，修改 Prompt 才改变。新 `material_model.definition` / `signature` 纳入完整要求；独立测试覆盖前述五类及模型变更：已失败调用锁定旧版本，每次定义改变新增版本，旧修订保持不变。结果未知同样锁定；只改显示标题不新增素材版本。

共享身份按准确复用引用及一致要求建立，不能只依据相同媒体哈希或名称。逐镜投影也不能把实体／状态的适用性展开为其全部素材使用；当前 `ui_projection.scene` 的 `add` 只接受明确素材需求或原件。动态增加实体／状态归属筛选符合“按实际归属筛选”，前提是只为本镜明确使用的素材出现；独立测试确认原本空选不会因此自动变回全选。

素材版本与候选的切换为同步操作，没有发现与 F-R03 相同的异步响应问题；历史实体、状态、关系及素材修订共用 `entityVersionControl`，因此受同一修复保护。没有把源码上不存在明显问题视为真实页面已通过。关系图的尺寸、底部边界、双击与键盘、三层位置和媒体停止仍须实际浏览器覆盖。

新评论资格只覆盖版本准确成员及完整定义的准确来源，独立测试确认复用链中间记录、新来源修订和错误版本不会被顺带授权。素材版本数量不因评论改变。同定义再次调用保持首次锁定的 provenance，旧来源上的评论继续有效。

另补跨实体读取兼容测试：如果接口已有明确 canonical 身份及其版本，即使共同素材不在当前实体的 requirements 列表，也能从该版本的准确 plan／definition_records 读取同一卡；不会把它加入当前实体采纳范围。这不计入当前历史数据缺陷。正常完整状态校验要求需求主体等于状态所属实体，定义比较保留 entities；因此不同实体主体的需求仍保持独立，未为显示共享而放宽合并证据。

## 独立媒体验收夹具与页面发现复核

基线中没有可用视频和多个可预览组成的组合。经主代理明确委派，独立审查代理用本机 ffmpeg 创建 `.runtime/ui-material-model/media-fixture`：一个完整视频版本、两个 4 秒有声色块候选，每个候选均有视频原件与 PNG 预览；另有一个标准测试图候选用于圈选。全部经合法媒体 ingest 和 production import 登记真实本地 CALL、候选及准确组件，未调用收费服务，未写入故事实例。标题、说明和 manifest 均标记“验收夹具 · 本地合成 · 非故事媒体”。制作命令与原件哈希保存在夹具 manifest，主代理独占浏览器操作。

主代理在该夹具真实页面发现：候选 A 选预览后切候选 B，旧 `detail.componentId` 使 B 也默认预览。主代理修复 `material-review.js`，按候选准确修订存取组件，仅为原记录保留旧定位兼容；评论定位也写入准确修订键。独立新增三项回归验证需求入口与素材入口的 A 预览→B 原件→A 预览，以及预览评论定位后切 B 不串组成，均通过。这是主代理页面发现的独立复核，不计入前述 13 项独立发现。

主代理随后修复准确 ASSET 链接刷新后采用入口缺失。独立代码复核又发现 `showProductionAdoption` 仍从全局 productionRecords 寻找素材，而素材管理的全局列表只含集场镜，因此入口恢复后表单候选为空；主代理同步在真实页面复现同一问题。修复后，素材卡向表单传递所选版本的准确候选，其他旧入口仍沿用原列表。新增两项独立检查确认无准确 matching requirement 时不出现采用入口，匹配时传入准确候选，且全局无 ASSET 时仍能选到这两项；采用没有传播至其他需求或状态。此项作为共同发现单独记载，未重复计入前述数量。

主代理还在真实图片圈选中发现跨素材返回后只打开需求、未恢复原 ASSET 评论焦点。独立审查建议仅在普通小卡入口、同素材同版本的合法评论目标中恢复，准确链接始终优先，正文已清除则不唤回。修复后的四项独立检查使用真实草稿记忆、焦点及卡片激活函数，验证图像锚点恢复、准确修订／版本链接优先、已清除草稿不重开，以及不跨版本或成员范围恢复。页面行为由主代理再验，本代理未操作浏览器。

第一版草稿夹具简化了正文存储键，未覆盖切换当前素材后旧焦点仍在的瞬间：真实页面发现再次记忆会把旧条目的素材版本键覆盖成 legacy 键。主代理增加上下文一致性保护；独立夹具随后改为直接执行 `app.js` 的实际 `legacyDraftKey`／`draftKey`，连续激活两张卡且不重置旧焦点或锚点，核对旧正文键保持并可返回恢复。该过程说明最小夹具的覆盖限制，真实页面复验仍不可省略。

## 全量恢复发现及独立事务复核

数据代理在实际完整 Schema 6 恢复中发现 P1：写入 78,889 个内容节点后，SQLite 回滚日志模式因缓存页写盘取得排他锁；`bundle.restore` 校验 metadata 时，`material_archives.resolver` 另开只读连接读取同库，触发 `database is locked`，恢复整批回滚为空库。小数据夹具没有触发页写盘，因此此前通过的小样不能证明全量恢复已完成。该发现来自数据代理的真实恢复，不计入前述 13 项独立发现。

修复在恢复写事务外层设置 `material_archives.read_scope(store)`。只有归档所属实例的实际数据库路径与当前 Store 完全一致时，才使用当前连接及内容缓存；异常通过 `finally` 清理 ContextVar，不把锁错误吞掉后改读其他来源。数据库事务及归档文件的回滚机制仍由原上下文管理器处理。实施者增加低 `cache_size` 强制页写盘的完整恢复回归；独立审查仅新增以下三项边界检查，未修改修复源码：

- 同一数据库真实 `BEGIN EXCLUSIVE` 时，独立连接确实被锁，而当前作用域可读取未提交的准确内容；另一真实实例缺少该内容或路径没有已知实例根时均拒绝，不借用当前库。
- 作用域内抛出异常后，数据库内容回到写入前；退出作用域及新作用域都不能读取已回滚的缓存，原连接仍可使用。
- 嵌套不同实例的作用域，内层异常退出后恢复外层上下文；外层保有排他锁仍能读取，证明使用的是正确原连接。

三项独立检查均通过，计入 Python 22 项。数据代理随后实际完成全量空实例恢复，耗时 397.746 秒；[恢复证据](../restore-evidence.json) 保留系统 `ff475e494a337f0e41038431d21c10382358fefa`、迁移 `e08255344127dfc5b0eaed3f5052a7b2400ac083ac32af187536bd69fdea69b5` 的真实执行身份。23 张导出契约表逐行相等、1,855 份归档原字节相等、1,314 份重新导出文件字节相等。既有故事私有表 `generation_publications` 的 2 行不在通用导出契约内，证据单列该边界，没有宣称已通过此格式恢复。

数据代理随后用非规范 JSON 发现另一个恢复缺口：旧 payload 虽可正确还原，实际插入时再次解析并编码会丢失缩进、Unicode 转义及 CRLF，样本从 1,441 字节变成 945 字节。当前 10,160 条真实修订恰为规范格式，不受此差异影响，但已有格式兼容仍必须保留原始字节。修复让 Schema 6 插入已经校验过的原物理 payload，让旧 Schema 2—5 插入已经核对修订身份的原 payload 字串；Schema 1 仍按其原始来源格式恢复。

独立审查确认内容节点哈希、逻辑修订身份、格式与准确引用、完整定义与索引、实际插入触发器及事务回滚均未移除。实施者的 Schema 6 原字节导出／恢复用例通过；本代理另加两项旧 Schema 5 回归：非规范 JSON 真正恢复到空实例后，物理与逻辑原字节相等，恢复后的同 ID 改写仍被校验触发器拒绝；篡改修订内容并重新计算外层文件哈希，也仍因 `revision checksum mismatch` 拒绝，目标对象与内容表保持为空。两项均通过，包含在 Python 22 项内。此发现由数据代理提出，未计入前述 13 项独立发现。

最终 b874b959 候选与上述全量恢复输入另作独立比对：除迁移日志身份之外对象表相等，内容图、评论、来源、配置及全部 1,398 个导出原件文件字节相等，1,855 个归档容器相等，见最终关联证据的 `actual_full_restore_reuse`。真实修订均为规范格式，因此原 JSON 修复不改变这批输入；新增非规范格式由两类针对性空实例恢复验证。没有将此前 397.746 秒全量恢复标记为在 b874b959 上重新执行。
