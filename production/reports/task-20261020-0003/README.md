### CPU、调用和字节归因

- 本机小图请求线程 CPU 暖态中位 **344.898 → 1.612ms，减少 99.53%**；不再逐媒体读取 7796 条历史操作的大 JSON。删除回执由准确格式索引查找并按事务代号失效。
- 本机成片 review 请求线程 CPU 暖态中位 **2392.668 → 203.900ms，减少 91.48%**。单次未命中投影 profile 的 CPU 为 **3.154 → 0.601 秒**；profile 有测量开销，不能与未插桩暖态混算。

- 全局实体 profile 的 SQLite execute 从 **11684 → 7263 次**，SQL 自身 CPU/墙钟采样累计 **5.428 → 0.179 秒**；整个 profile CPU **8.646 → 0.950 秒**。批量准确归属查询取代逐镜扫描，保留所有 416 镜范围。累计函数时间存在嵌套，不能相加作比例。

两端实际配置来自容器只读挂载，不能拿实例目录的占位文件代替。原资源配置/目录与本次候选哈希相同，发布窗口再次复核；instance.json 保留各端自己的字段，只前进系统 pin。本机 task-20261020-0002 的三份 content 挂载仍是运行依赖，不能清理其目录；VPS usage、Nginx、Xray 与资源限额保留。

第一次本机切换未开放新服务：创建新容器失败后的核查发现，旧 CA 证书的宿主路径已成为目录，阻止原容器重新启动；Docker 返回小写 `no such object` 也使原恢复判断拒绝继续。原创建错误未保留底层 stderr，不把其准确原因记为已证实。已用原镜像内 CA 证书建立项目运行目录中的稳定文件，克隆原容器且仅替换该 bind 源，恢复旧代码并核对全部业务表指纹不变，再释放 HTTP 写入锁。修订发布器在停服前核对所有宿主 bind 与运行容器内目标的文件类型，并兼容 Docker 缺失对象错误的大小写；4 项针对性回归通过。后续准确候选、独立补验与切换事实见 [发布安全补验](independent-review/release-recovery-followup.md) 及主项目运行回执。失败发布包和恢复记录不被覆盖，未回灌数据库。

任务私有数据库、恢复副本、下载缓存、临时测试容器和代码包在提取证据后按准确归属清理；不全局 prune，不删除正式原件或其他任务资源。最终保留项及数量从运行清理回执取得：正式运行及受控回退镜像/前任容器、既有完整恢复介质、最小采样与审阅证据；worktree 待会话退出释锁后受管退役。旧独立复验、历史测试迁移、内容/感官质量残留沿原任务责任，不由本任务自动关闭。
