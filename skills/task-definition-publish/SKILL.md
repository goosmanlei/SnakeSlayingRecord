# 任务定义与发布

让执行者不依赖旧聊天，就知道要解决什么、改后怎样工作、做到哪里才算完成。证据充分、限制完整不等于任务清楚；发布者须完成必要的产品与创作判断，不能把尚未定义的目标藏在“优化、统一、按价值整理”中交给执行者。

本方法接受用户直接提出的需求，也承接 `creative-system-review` 的发现。两者按目的分工：Review 通过真实创作和使用发现、查明问题，本方法为形成高质量任务继续调查研究。无需等待一份完备调查报告才开始，也不重新全量巡查已经查清的事实。项目依据与受管发布入口见 [项目衔接](references/project-context.md)。

## 为任务决策调查

先理解人正在完成的工作、希望获得的结果和本次授权。回读准确现场与已有证据，区分用户决定、已验证事实、推断和候选方案。旧任务中的产品选择只用于理解历史，不自动覆盖当前要求。

围绕会改变任务定义的缺口开展调查：问题在当前准确版本是否仍存在；正常对照怎样工作；已有表达、操作或工具能否复用；上下游和不同入口是否需要同一改变；候选方案能否完成整项工作、会增加什么成本。需要时查作品、方法、页面、数据关系、代码和实际回执；技术分析辅助判断，不能冒充看过、听过或操作过。复用仍适用的证据，版本或条件实质变化再补验。

调查不仅寻找缺陷，也应帮助选择方案。先考虑删除多余要求、复用、自动处理，再考虑新实体与流程；比较对用户结果有实质差别的方案并作出有依据的取舍。能在现有委托内自行查明和决定的直接推进。确需用户决定的创作偏好、范围或授权，带着事实、方案及影响询问，同时继续独立工作，不把每个任务变成一次审批。

调查做到足以稳定目标、必要范围、关键选择和验收即可，不要求查完所有技术细节。若新证据改变了原问题，应调整任务；问题已不存在、已有任务覆盖或收益不足时，不为产出数量发布。

## 定义完整的改后工作

先用一个具体工作说明当前障碍、选定的改变、改后结果和收益，再确定实现这一结果所需的范围。共同原因和共同验收支持合并时，按完整用户目标组织；只证实局部就保持局部，不用宏大标题扩大结论，也不把结构性目标拆成一串无法共同兑现结果的小修。

根据任务性质，把影响结果的选择说清：

- **界面与流程**：从哪里进入，先看到什么，哪些信息或入口删除、合并或复用，默认对象与范围如何确定，主要动作之后怎样反馈、保存与返回。跨入口、类型或状态有差异时说明差异；“当前用途”“保留回查”等词必须有可操作含义。每项信息说明它服务的判断，删除展示与删除数据分别决定。用户要求不折叠时，逐项判断信息必要性，不能以全部展开、改名或搬到其他隐藏容器代替简化。
- **行为修复**：给出准确输入、触发步骤、实际错误与正确结果，以及必要正常对照。例如选中两段正文后反馈引用混入未选字段，期望应明确为仅保留真实选中文字，并在保存、刷新、重开与定位后保持一致。
- **创作与方法**：明确准确作品依据、想改变的表达及上下游承接，按适用专业方法安排真实工作顺序。例如本镜只演放下诱饵、抽手、关门，提闸发生在下一镜；验收需连看这两镜，不能只写“单镜正确”。不能把一次批量填充当作逐步理解、创作和修订。

这些是判断提示，不是每项任务必须填写的字段。具体程度应让执行者无需重新决定关键产品方向，同时保留实现、组件和代码组织的选择空间。明确设计不代表设计有价值，仍要用实际工作检验。

较大或有不确定性的改变，先用可操作样例检验目标体验，再检查不同入口、类型和关键状态能否按同一方案工作。说明样例支持了什么、扩展还需解决什么；不能把一个样例自动外推到全模块。尚未验证的方案可以保存为草案；影响关键取舍的缺口由任务定义者继续调查，不用“执行前补查”将它转交给实现者，也不把草案直接作为已澄清的实现任务发布。代码根因、组件选择等不影响已定结果的调查可留给执行者。确实需要独立实验时，按授权定义有明确问题、边界和结束判据的研究任务，不以研究结论未定的任务承诺完整实现。

## 用前后例确定完成条件

验收先回答用户能否顺利完成原工作，再检查必要的准确性、保存与保护能力。把选定方案落实为可读、可看、可听或可操作的前后例：在什么内容、版本和环境下，怎样走完路径，过去卡在哪里，改后应看见什么、做成什么、减少什么负担。预期效果与已经实测的效果分开写，不编造精确提升数字。

例如，简化任务不能只要求“减少信息负担”。应依据已验证方案写清：打开一场时，哪些必要条件只出现一次，怎样接着读各镜动作与独有选择；当前决定在哪里表达，追查一次旧决定如何到达、读清并返回。先明确这条工作路径，再列出需要覆盖的同类入口与例外。示例说明具体程度，不预设本项目任何页面已经具备这条路径。

范围包含多个类别时，让验收对应这些类别和关键差异，避免只验样例。视觉、声音和交互效果需要相应实践，源码与自动检查只作补充。环境不可用、未授权生成或部署属于真实边界；承诺的核心结果尚未实现属于未完成，不能改称“限制”后结项。执行者完成报告、正式交付和独立复验通过是不同状态。

明确本任务交付到可审候选，还是包含正式环境生效；用户要求实际可用而当前只授权候选时，说明后续尚需什么，不把候选完成写成用户已能使用。验收环境与交付终点必须匹配。

## 写成执行者可直接使用的任务

正文按理解任务的顺序组织：原问题与改后结果，必要范围与已定取舍，依据和真实工作步骤，具体验收及交付边界。长度随任务调整，不强制固定模板或章节数。标题表达对象和实际改变，不能只写“优化体验”。

调查过程、历史误判、任务沿革、完整哈希与回执放在已有证据附件；正文保留判断所需的事实与准确入口。授权、保护内容、输入锁和影响成败的约束不能省略。共用工程流程引用项目唯一入口，不在目标、步骤、验收反复复制；禁止事项不能代替正向方案。

发布前以不知旧聊天的执行者视角通读：能否复述改后工作、关键选择和完成条件？还需猜测哪些产品决定？正文、样例与验收是否一致，资料能否按入口取得？修复实际缺口，不以文字长度、字段数量或形式审阅代替判断。

## 发布并交接验收

发布前回查当前任务账本、在途修改和实际交付，按目标、行为与范围查重，不仅匹配标题。已有任务明确承担的内容不另发；已结项任务有确切残留时核对证据并明确后续归属，不能因 completed 忽略，也不凭本次未复现宣称修好。不得自行恢复已撤销任务、改写在途承诺或换编号重发同一撤销范围。

按当前授权完成任务文档、必要媒体及仓库范围登记，通过现有受管流程发布并回读。分别判断工作区隔离、修改重叠、真实依赖和共享运行资源：依赖为空不代表可同时写正式库，涉及同一仓库也不必强制串行。发布任务只建立可承接的工作，不代表已执行或部署。

任务必须要求最终回复先写**任务编号和实际解决的问题**，再以具体前后例说明变化、收益、实际验证的版本与环境、未解决事项及下一步，并按项目规则交代过程资源清理。为回收者留下准确交付与证据入口；Review 沿原工作独立复验，结果再进入后续判断。不得仅以测试通过、增加可打开的说明或“执行者报告完成”代替效果验收。

仅获准定义或发布时，到相应交付与回读为止；不调用 `codex.task do/run/mrun` 代执行，不因本方法自动启动持续 Review、付费生成、正式内容修改、部署或外部发送。已获授权的调查、取舍和发布直接完成，不重复索要逐项许可。
