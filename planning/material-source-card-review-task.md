# 按需求来源贯通素材卡与准确引用

## 用户目标与预期价值

审阅者从镜头、实体或素材列表打开某项素材时，应能看到指定的准确需求、方案版本与候选，并在同一需求来源下连续审阅相关素材。大卡左侧回答“这些素材为什么需要”，右侧回答“当前素材如何制作、哪个版本或候选可用”。需求来源指实际产生需求的实体、实体状态或视听镜头，不等同于画面里出现的人物。

统一现有卡片的来源投影和交互，消除准确引用的假缺失，减少同来源素材之间关闭、搜索、重开的操作与记忆成本。没有操作耗时对照，不承诺节约百分比。界面方案须先说明每项保留或新增信息支持什么判断，再用简单原型或可运行候选验证；沿用共用卡片和已有切换交互，不增加重复管理页、重复说明或第二套卡片。

## 已确认问题与证据边界

以下发现来自 2026-10-09 系统 Review 的正式 Chrome 操作和独立数据核验。观察时正式系统修订为 `edeeedd4c718b55b67c5814eddab6d4923ab8387`，系统主干为 `bf4fa9c963106293f0afd28fd5623717e6ca1d97`，后者另含四次体验版相关提交；版本差异本身不构成部署缺陷。执行时以最新主干和准确正式数据重新核实，不将观察版本或数量固定为开发基线。

### 实体级准确需求被卡片投影遗漏

从 ASH001 的本镜素材打开 M2624，以及正式页面另一次打开 M2627，均出现“准确素材标识不存在；未替换为其他素材”。需求和准确版本真实存在。卡片接口的 `detail.material_versions`（素材详情的方案版本集合）包含该项，`entity_review.material_versions`（实体审阅卡的方案版本集合）却没有；前端优先使用后者校验，造成假缺失。

与正式镜像、业务快照一致的隔离接口完整检查了 127 个需求来源实体：166 个实体级需求全部被相应投影遗漏，包括 110 个身份／结构需求、16 个空间需求、40 个音色需求。166/166 的分子为投影中未出现的需求数，分母为该快照全部实体级需求数；这是接口遗漏范围，不能写成 166 次浏览器失败。修复须核对当前完整需求集合、列表与计数，不能只给两个示例加例外，也不能补造新素材。

### 同镜需求未在同来源大卡汇聚

M2973、M2974、M2975 分别是 ASH001 的主机位、首帧和视频需求，均指向同一准确镜头修订。接口的 `adoption_context.requirements`（审阅采纳上下文中的需求集合）包含三项，但每张大卡只展示当前一项。正式页面从 M2973 打开时，左侧只有镜头和 M2973，没有同镜首帧与视频的切换列表，审阅者必须关闭重开才能查看相关需求。

### 历史音色的有效来源被退役占位遮蔽

沿“素材管理 → E17/S040 → 声音 → 有结果 → M1134”打开已有音色，左栏显示“历史原件未登记实体或制作位置归属”，关联用途显示 `form-a-heng-blue`、`form-a-heng-later`、`form-a-heng-wet` 裸标识。继续点击能够打开正确的历史状态正文，属于来源表达错误与中文标题遗漏，不是原件丢失或链接悬空。

M1134 对应 `asset-fg3-aheng-voice-01`，准确修订为 `e522f05e989232e8323608cc74addd94b5e542c15c2d69692109c5fdd3e78ecb`。它保留 EN002 阿蘅的主体归属，以及 ST088 日常洗旧青衣、ST090 点名后日常、ST092 捞书后湿衣袖三项状态覆盖；准确状态正文仍可读取。旧需求列表包含已退役的占位，首项需求的 `scope`（需求来源归属）为空，却使来源分支提前命中，跳过有效状态覆盖与人物主体的回退读取。接口已有中文标题和业务编号，关联用途渲染未使用它们。

上游 Review 补充的同轮全量检查覆盖 296 个现有 ASSET（历史原件对象），包括 252 个图像与 44 个音频。它们均具有有效、准确的主体归属 `subjects` 或状态覆盖 `state_coverage`，但卡片接口的 `scope` 与 `entity_review` 均为空。296/296 的分子为上述两个来源字段均为空的原件对象数，分母为本轮全部现有 ASSET；单并发完整检查没有请求错误。它与前述 166 个实体级需求是两种对象，数量不相加，也不能写成浏览器失败次数。该证据说明历史原件来源投影的覆盖范围，不把 M1134 的具体分支原因未经复核推广到全部对象。

M1134 的旧依据与准确认可继续保留；新音色需求 M2669 的方案和候选关系独立审阅。本任务不建立 M1134 到 M2669 的候选复用、已选输入、结果候选、认可或采纳迁移，不改写原件生成时记录。

## 修改范围与实现原则

- 实体自身产生的需求须在实体卡中有自然位置；实体状态需求继续归所属实体，并保留状态层级与准确依据。当前支持的视听镜头等非实体来源，按实际来源汇聚完整需求，不能伪造实体来源或按画面中出现的人物归组。
- 同来源需求共用左侧来源与需求列表；切换右侧准确需求、版本或候选时维持来源上下文。列表、计数、卡片投影和引用校验采用一致的需求身份与版本语义。
- 修复历史原件来源选择分支：无有效归属的退役需求占位不能遮蔽仍有效的准确人物或状态来源。关联用途使用现有中文标题与必要业务编号；没有证据的归属仍明确未知。
- 参考小卡、Prompt 中固定到具体对象与修订的引用、素材管理、实体管理、故事相关制作入口和准确深链继续共用卡片契约。真实失效的对象、版本和候选仍明确拒绝，不回退到最新、同名或其他素材；历史版本可独立查看。
- 评论、草稿、选中状态、阅读位置和返回入口随准确对象维护。汇聚展示不改变采纳动作的范围，不扩大历史认可，不改变既有采纳事实。

根因复核入口在通用系统 `review_desk/ui_projection.py` 的来源与卡片投影、`review_desk/generation.py` 的实体需求读取、`review_desk/static/unified-cards.js` 的准确引用校验和非实体分支，以及 `review_desk/static/material-review.js` 的关联用途标题。它们是调查线索，具体实现以执行基线复核为准。

任务不涉及剧本、制作内容或新媒体生成，不需要真实付费调用；素材编号搜索、镜头标题整理、AI 润色参考及历史候选复用等其他 Review 问题不纳入本范围。不得通过删除准确校验、改写历史数据或单一样例硬编码完成修复。
