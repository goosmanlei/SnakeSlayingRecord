# 新一轮审阅台自主优化：Astra ultra

## 目标与执行配置

本轮继承 `task-20261004-0002` 的自主优化方式，待同项目 `task-20261004-0009` 完成后，从本任务首次 `task mrun` 开始执行时的系统出发，自主发现、解决并验证影响日常创作审阅的问题。用户通过界面了解进展、阅读或试听成果、评论和作出判断；Codex 与后台程序推进创作、维护数据并迭代审阅台。让既有功能更符合这一分工，减少无目的的展示，统一页面和交互，使数据概念与真实创作流程一致；同时测量并优化各主要页面和功能的加载、切换、渲染、交互及后台读写性能。

本任务执行时采用一个主协调会话，内部自行安排监督、独立审查和 worker。主任务为 `gpt-6-astra / ultra`，子代理默认继承同一模型与强度；按可用并发安排有界任务，默认同时工作的角色不超过四个。优先级 P1，复杂度极复杂，同项目依赖为 `task-20261004-0009`，不允许与其他任务同时执行。没有新媒体输入，也没有新增付费创作授权。

`ultra` 按当前 `codex.project` 的极复杂任务映射发布，不复用上一轮的一次性发布例外，不修改通用模型映射或调度机制。主协调负责共享实现和契约，监督负责时间、方向与证据，worker处理明确范围的问题，独立审查者复核非本人实现。相对 max 的预期收益是分担历史调查与审查，减少遗漏及自验偏差，并让历史与性能瓶颈调查、审查和部分实现并行；这些收益未经本轮对照实测，不承诺固定提速或质量提升。报告必须记录实际分工、有效独立发现、修复复验、并行范围及协调等待、冲突和返工，持续争用时缩小委派。共享写入归属和浏览器操作窗口由主协调安排。

任务执行、恢复与完成状态以主项目任务账本为准，本文不维护另一份状态。本会话仅澄清及待确认发布，不启动实验。新任务摘要为“以 Astra ultra 自主优化审阅台体验与性能，监督运行6至10小时并交付完整报告”。依赖与并行理由：前置任务正在改变全站共用卡片、素材版本和历史存储；本轮跨层优化尚无与其他任务互不影响的确定边界，独立 worktree 无法消除契约和共享正式资源冲突，故按独占执行。任务内部有界分工与外部任务并行分别判断。

## 启动、恢复与基准

1. 阅读有效 `AGENTS.md`／`AGENTS.override.md`、`KNOWLEDGE.md`、`STATE.md` 及本说明，运行 `codex.project context check`。用启动提示中的 `_bind_session` 命令绑定本任务真实会话。不要手写任务账本或伪造会话环境变量。
2. **在任何优化、冲突修复或委派前启动本任务时间控制工具。** 运行 `python3 scripts/autonomous_optimization_guard.py --help`，依 [运行工具说明](autonomous-optimization-runtime.md) 的 `start` 命令传入启动器给出的主项目和 task ID。T0 来自本会话首次任务执行事件，不能使用可能早于执行的澄清会话创建时间。随后 `status` 核对首次启动时间、6／9／10 小时节点及监督进程状态。无法确认计时或监督生效时先排除问题，不在没有时间控制的情况下展开实验。
3. 检查现有 Goal：已存在本任务 Goal 则恢复它；没有则使用 `create_goal` 建立持续目标，内容包含本文件、基准范围、时间边界、独立审查和运行报告。不得覆盖其他未完成 Goal，不设置用户未要求的 token budget。本文件明确授权持续 Goal 与内部子代理；每轮汇报后继续执行，不能因一批改动完成就提前宣告实验结束。
4. 在本 worktree 的 `.runtime/autonomous-optimization/` 保存基准、发现清单、覆盖矩阵与检查点。记录实际已启用页面和主要用户路径、故事与系统仓库提交及差异、正式服务真实版本证据、正式数据一致性备份及关键历史数量。实例配置中的版本引用不单独证明服务实际运行版本；无法确认的项目记为未知。
5. 以主项目根目录为基准定位相邻 `../story-review-desk-python`，读取其规则并为本任务建立系统仓库独立 worktree。嵌套任务目录不能直接套用相邻路径。故事工具留在故事仓库，通用展示／评论／数据管理留在系统仓库。预览数据库、文件和端口均隔离，参照 [工作区流程](../production/generation-workspaces.md) 的正式快照与恢复方式，不覆盖活库。
6. 恢复时先读时间状态、运行报告和最后检查点，再核对未完成操作与实际 diff。T0、基准、问题 ID 和原有证据沿用；新增并行成果只做兼容性核对，不自动扩大为本轮新功能。已经截止只整理已有结果和交付，不重新优化。

## 问题发现与自主调度

先读 [历史意见重点](autonomous-optimization-focus.md)，再从可取得的历史会话、原任务说明与准确评论核对原意及后续替代关系；来源缺失时如实注明。六类重点是主动调查方向，不是预先认定的缺陷列表；先核对意见有效性和当前行为，再提出问题。无评论的页面也检查。创作内容意见只提炼可读性、目的、依据和因果等通用要求，不借此改写小说、剧本、歌曲或接受作品。

协调者负责覆盖、优先级和有界分工；监督者检查方向、时间、证据及是否增添无必要概念；worker 实现明确问题；独立审查者回看实际 diff 和用户场景。角色可以由少量代理复用，修改者不能成为自己改动的唯一验收者。给子代理的初始指令须先等待登记回执，不得直接开始实现。创建后立即登记到时间工具，验证成功再授权其执行；子代理自行再委派时，将后代 ID 回传主协调登记；子代理不得绕过根会话身份校验直接执行 register。停止时包括所有登记后代。

每个问题记录：稳定 ID、用户场景、当前与预期行为、证据、对应原则／历史意见、影响、建议改动、验收方法和处置结果。优先处理阻断审阅、误导判断、数据或历史错误，再处理反复遇到的交互与一致性问题；纯个人审美偏好不能自行当作缺陷。未经核验的现象标为待核实。

每批按“发现 → 核对价值与依据 → 实现 → 验证 → 独立审查 → 报告与检查点”推进。任务按文件或模块明确写入归属；同一工作区同处写入及有真实先后依赖的修改串行；不同工作区的有限重叠按冲突概率和幅度判断，允许可控冲突后集成复验，不仅因涉及同一模块就串行。独立调查可并行。不用多个代理重复相同全量检查消耗时间。监督者可以驳回收益不足、扩大范围或证据不充分的改动；驳回和撤回的原因也进入报告。

允许删除冗余 UI、重组页面、重构代码、兼容地调整数据结构和 API，同时维护调用方、数据迁移、导出和恢复。保留有价值的能力、业务语义、真实原件、评论、不可变修订、实际调用和准确采用。取消整项能力、改变创作方式或推翻明确偏好时，提出具体取舍供用户判断，继续不依赖该决定的工作。没有必要就不增加新实体、状态层、入口、说明、监督界面或调度框架。

本轮不得与其他任务同时执行。内部代理在边界明确后可并行调查及有界实现；共享位置写入与浏览器操作按序安排。共享正式数据库、部署入口、3000 服务和双仓集成串行协调；没有额外授权时本轮优化只产出经过验证的候选，不提前切换正式服务。测试评论和采纳只在隔离实例，正式发布使用最新输入的增量，不以任务快照覆盖活库。

## 各主要页面和功能的性能优化

性能优化与体验、正确性优化同为本轮目标，不只处理偶然遇到的慢接口。执行时按实际启用功能建立覆盖矩阵，包含制作思路、故事创作、制作设定、全剧制作、系统管理的主要页面和子页，以及共用导航、卡片、弹窗、评论与媒体功能；不适用项说明原因。

按用户操作检查首次加载、导航和版本／集场切换、筛选与列表、长正文和逐镜渲染、实体素材卡与关系弹窗、评论与定位、采纳、媒体预览。分别定位网络请求、服务处理、数据库读写、返回体积和前端渲染等实际瓶颈；先测量再决定优化，不根据代码形态或主观观感预设缺陷。优先减少用户等待、交互卡顿和不必要的资源消耗。

性能对照在独立预览实例进行，记录机器及负载、浏览器及视口、代码版本、数据规模、缓存是否已有内容、测量起止点、样本数和重复次数。前后使用相同数据和场景；记录原始耗时、代表值及波动，少量样本不包装成可靠尾部统计。真实浏览器测量从用户操作到内容可用的效果，接口耗时只证明相应后台路径。主协调安排测量窗口，避免其他子代理的测试或计算负载干扰；调查和分析可并行，前后性能测量按序执行。

每个已完成优化须给出基线、瓶颈原因、改动和同条件复测，收益应超出测量波动，并复核受影响路径没有未解释的明显回退。不得通过删功能、漏数据、少显示正文、放松校验、丢失历史或返回过期缓存换速度。缓存与索引等调整验证准确版本、变更后读取和并发写入；保留评论草稿与锚点、采纳／采用和完整媒体能力。性能审查由非同项实施者复核。

报告逐页逐功能交代测量和处置：已优化、未发现值得修改的瓶颈、未证实收益、受阻或待解决分别说明。性能工作同样纳入6／9／10小时边界，不延长运行；未达标准如实收尾，不预设固定提升比例，不为凑成果制造改动。

## 时间边界与收敛

本实验采用连续墙钟时间：首次 mrun 执行会话开始为 T0，等待工具、暂停、断线和离线均计入；恢复不重新计时。发布准备不计入。用户明确结束优先于 6 小时下限。

| 阶段 | 要求 |
| --- | --- |
| T0 至 6 小时 | 持续有价值的走查、修复、独立审查与回归；不能正常提前完成，也不能睡眠、重复无变化检查或制造改动凑时长 |
| 6 至 9 小时 | 满足下列收敛标准且报告完成，可以结束；否则继续高价值问题 |
| 到 9 小时 | 强制进入自检与收尾：停止新大项，冻结范围，核对遗漏、实际 diff、兼容性、报告和交付候选 |
| 9 至 10 小时 | 只做有限的已有交付阻断修复和必要验证；不能为完成所有想法不断延长 |
| 到 10 小时 | 停止优化及子任务；暂停持续 Goal，保留候选、完整到当前检查点的报告和截止回执 |

时间工具只监督本任务与已验证的后代，会在 9 小时向当前运行回合提示收尾，在 10 小时暂停自己的 Goal 并中断活动回合。断线、休眠或服务不可达时不能声称已经远程停止成功：保留错误与待重试状态，恢复后先补执行截止检查。不要启动跨截止点的无界 shell、外部生成或长时间写入；中断模型回合不等于撤销已提交的外部操作。每批结束和每次委派前主动查询时间及监督心跳；未结束却无法确认监督存活时先恢复监督，再开展后续优化。保证主要收尾在硬截止前完成。

正常收敛要求：基准全部主要功能与相关重要状态已检查；影响核心原则及主要流程的实质问题已关闭；界面变化经真实浏览器操作，数据变化经历史／调用方／必要恢复验证；主要页面和功能的性能覆盖、已修瓶颈对照及回退检查具备证据；独立最终审查没有未解释的高影响问题；剩余项均有明确依据和处置。不能以测试数量、主观分数或已运行时长代替证据，也不能把浏览器受阻记为通过。

正常结束先完成报告和候选，核对已过 6 小时且尚未到 10 小时、子代理已收尾，再将确实实现的 Goal 标为 complete，并运行时间工具的 `finish --reason converged` 撤销后续提醒。用户提前停止使用 `user_stop`，暂停 Goal，停止子代理并交付已有结果。截止使用 `deadline`，不能把未达到的质量目标标为完成。具体 CLI 以工具帮助为准；结束原因不可混用。暂停或暂时离线不等于用户要求结束，不重置时间。

## 必交付报告与最终交付

采用 [报告模板](autonomous-optimization-report-template.md)，首次执行先按本任务 ID 初始化新正文，不把上一轮已有报告当成本轮结果；随后持续维护 `planning/autonomous-optimization-run-report.md`。每批开始前登记问题和计划，验收后更新实际结果；报告保持可独立阅读，不能等到最后才从零回忆。首份完整报告形成后就在进度回复中给出固定文件链接，收尾前再次给出，确保截止中断后用户仍能直接访问；不要依赖最后一次聊天回复才暴露交付入口。9 小时开始逐项核对报告与 diff，正常结束或硬截止前完成定稿。提前结束、异常中断时交付最近完整报告及时间工具的停止回执，明确最后覆盖时点和未复核部分，不继续扩展优化。

报告必须回答：本轮改了什么，原来有什么问题，预期有什么收益，实际证实了什么；发现了哪些未改、部分修改或撤回的问题，为什么没有继续，影响与下一步是什么。按用户场景或六类重点组织，避免用提交清单、原始工具日志和未定义术语代替解释。预计收益与实测收益分别表达，不编造节约时间或提升比例。每项发现均有结果，所有最终变更可追溯到问题、证据及候选。

报告还须说明起止时间和经过时间、基准与交付版本、覆盖范围、验证受阻项、剩余风险、是否已集成／部署及预览入口。截图和技术详情按需链接；绝对路径仅用于工具需要或项目外资源，项目内使用相对路径。不把本报告混入面向创作用户的产品 UI。

结束原因分别记为达到收敛标准、时间截止、用户结束或异常中断；结果未达标不能包装成成功。先更新必要知识和当前状态、完成双仓候选与有意义的验证，再按 mrun 原有 `_prepare_integration` 流程准备最终候选。展示报告、预览与证据，等待最终明确确认后再集成、推送和切换正式服务；确认等待在自主优化时限之外。`_complete` 成功后只回读，不补写已确认候选。

本任务不保证机器休眠、账号限额或外部服务故障下仍可持续计算；这些情况必须写入报告，并按原截止时间收尾，不能用无限恢复把十小时实验变成无限任务。

## 可验证的完成标准

1. 启动基准可复核：既有页面、主要流程与重要状态有覆盖矩阵；两仓代码、实际服务与一致数据快照分别记录。历史意见有原始来源、有效性和检查去向，不把旧已修问题当现存缺陷，不推断未知评论作者。
2. 时间工具与持续 Goal 生效；首次执行T0持久化，6／9／10小时连续墙钟边界正确，恢复不重置，9小时开始收尾、10小时停止本任务与后代；手动结束撤销后续提醒。任何服务失败、离线和未完成停止如实留证，不误影响其他任务。
3. 按用户价值自主发现与小批优化，修改者不独自验收；任务内部有界并行与双仓隔离成立。所有新增展示有明确目的，不引入重复入口、第二套评论系统或不必要概念。有效能力、业务含义、准确历史及后台流程保留。
4. 收敛须覆盖基准主要功能与相关状态，关闭影响核心原则和主流程的实质问题，经独立最终审查无未解释高影响缺口。界面改动真实浏览器验证；数据与API变化完成针对性兼容、历史及必要导出恢复检查。未验项不得写为通过；正常质量完成不得早于6小时。
5. 本轮运行报告为独立可读正式交付：每项实际变更解释问题、变化、预期收益与已验证效果；每项未改、部分处理或撤回发现说明证据、影响、具体原因、优先级和下一步；报告与最终diff、时间回执、候选和部署状态一致。无虚构收益数字，无遗漏发现，原始日志不能代替解释。
