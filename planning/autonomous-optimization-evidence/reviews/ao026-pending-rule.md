# 相反变更复核的契约核对

结论：这是正常界面能够产生的冲突，不仅是人为导入的 API 反例。现有基础存储已支持“同一个复核对象创建新修订并保留旧结论”，但文档没有规定同一 target/old/new 只能有一个复核对象，也没有定义多个独立复核的冲突优先级。因此可以直接修同次提交的重入与重试；不能据此自行把全部历史复核改成“最后一个人说了算”。

## 两项实际复现

`decision-ui-probe.cjs` 加载真实 production.js，调用真实编辑器与保存按钮：选择 keep 并保存，在请求未返回期间同一编辑器选择 rework 再保存。保存按钮和 action 均未禁用，正常回调立即发出两次 POST；target/old/new 完全相同，两个 object_id 不同，expected_version 都为 0。结果与准确请求在 `decision-ui-results.json`。不需要直接调用伪造冲突的 API，也不需要两个操作者。

`contract-probe.py` 的新增最后一项使用正常导入契约创建判断 ID `mutable-decision`：第 1 修订 keep，第 2 修订 rework、expected_version=1。查询当前头只有 rework，该 target 重新待复核；历史仍为 `[rework, keep]` 两个修订。说明基础数据模型可表达更新，无须新实体或新历史系统。它不能自动解决已经存在的多个不同 ID，因为另一个 ID 的 keep 仍会生效。

## 不擅改业务契约的最小范围

1. 同一个打开的编辑器只允许一个提交在途，提交时冻结 action/actor/reason 的准确快照；同次未知结果重试沿用请求 ID，防止生成新的独立判断。此为提交正确性修复，符合已有操作含义，不必询问用户。
2. 保存后的刷新、错误提示和关闭仅作用于仍属于该编辑器的上下文，避免迟到回执清掉新范围。本轮此前已给实际失败证据，同样无需引入业务判断。
3. 后端可用已有 expected_version 更新一个已明确选中的判断对象，保留旧修订；但不能自动从多个不同 ID 中任选一个、改成稳定业务键后忽略剩余 keep，或按本机时间挑胜者。
4. 若本轮只修 1/2，应在运行报告准确保留“不同独立判断相反时缺少统一裁决规则”，不能将 UI 防重入写成跨窗口冲突已经解决。若要连这项也闭环，需要先确立下面一条业务规则，再实现必要的原子校验与兼容处理。

## 建议根提出的具体判断题

**同一使用位置、同一对上游旧／新版本的变更处理，是一个可修订结论，还是允许并列意见？**

- **一个可修订结论（建议）**：复用已有判断对象和 expected_version，明确修改产生新修订；旧窗口不能覆盖新结论，原历史全部保留。遇到既有多 ID 的矛盾历史先要求明确选择处理，不自动按作者或时间合并。
- **允许并列意见**：保留每份独立判断；keep 与返工／替换意见冲突时维持待复核，需明确解除冲突后才能继续。它需要确定如何解除冲突，不能仅显示提示而永久无法处理。

建议优先第一项，因为现有对象修订和乐观版本已足以承载，界面也在让用户选择一个处理动作；但这是根据现有交互作出的建议，不是已被文档证明的规则。选择全局唯一结论或并列意见会改变多个合法判断的业务解释，因此应向用户提这个具体问题；修复同次提交重入和迟到刷新不依赖其答案，可以继续。

本轮只读诊断与临时探针，没有实施上述方案，没有改正式数据或判断历史。
