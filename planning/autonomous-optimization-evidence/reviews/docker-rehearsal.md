# 隔离 Docker 发布机制验证

修正后的发布脚本能够使用本机固定基础镜像构建准确代码树。独立技术实例已实际完成旧镜像启动、候选镜像与两个只读文件挂载切换、健康读取和恢复；恢复保留了切换后新增的技术评论。正式服务没有切换，最终候选尚未由这份演练发布。

## 验证对象与发现

最初脚本 `release.py` 的 SHA-256 为 `e981564e8dd72d85b97b99424b9ae992acaf12ab05959144c04388aee43af422`。Dockerfile 直接使用 `FROM sha256:2ea67ae30f93796f1ca85ab7e549552e585273d8f95bd0a26a0285ae89fbdeeb`。在本机 Docker 29.8.0 的真实构建中，即使传入 `--pull=false --network=none`，BuildKit 仍将其解释为 `docker.io/library/sha256:<id>`，进入远端镜像元数据与鉴权解析并失败，耗时 6.56 秒。该结果是实际发布阻断，不是离线测试的推测。原始输入和错误保存在 `build-input.json`、`build-results.json`、`build.log`。

作者随后增加任务专属、包含完整镜像 ID 的本地基础标签，并在构建前后核对标签仍指向该 ID；若同名标签属于其他镜像则拒绝覆盖。修正后的脚本 SHA-256 为 `c4ddc127bb004c1f8484870c02b9e5635fc128905b258013a6b027311d61953d`。

`wrapper_build_recheck.py` 直接执行这份脚本未替换的 `build()`：实际读取并核对诊断包、固定基础标签、执行 Docker 构建、以 `--network none` 启动一次源码校验容器，并写出镜像回执。整个入口耗时 0.925 秒，42 个源码文件与系统已存在提交 `10a11aa27547e11be783a35e4ce2aac29d042927` 完全一致，基础标签前后仍指向固定镜像。结果及准确镜像 ID 见 `wrapper-build-results.json`。

这份诊断包明确标记 `diagnostic_only`，使用真实已有提交标识、合成配置和准确代码树；缺少正式发布所需的仓库、目标分支及发布字段，不是经 `prepare` 产生的最终交付包。没有用虚构最终提交调用 `prepare`，也没有调用 `preflight`、`apply`、`recover`。

## 真实切换与恢复

`compose_probe.py` 复用旧脚本的纯 `compose_definition()` 输出，所有主机路径输入均指向本目录新建的技术实例、合成 CA 和候选文件。输出只将两个 nginx 映射端口改为 `127.0.0.1:49448` 与 `127.0.0.1:49449`；命令使用独立 Compose 项目 `ao-task-20261004-0002-docker-rehearsal`，并禁止拉取镜像。准确差异见 `structural-differences.json`。没有调用脚本中绑定正式项目的 Compose 或健康验证方法。

约 58 秒的完整演练实际通过了以下路径：

1. 固定旧 app/nginx 镜像启动，两端口能够读取技术实例。
2. 切换候选 app 镜像，准确挂载 `config/instance.json` 和 `content/production-approach.json` 两个候选文件；API 呈现候选内容，容器内文件哈希一致，对两个文件尝试打开写入均得到只读文件系统错误。其他实例数据仍通过既有实例目录保存。
3. 运行中的 42 个源码文件与构建输入完全一致。
4. 通过真实 HTTP 在技术库新增一条评论。
5. 恢复旧 app/nginx 镜像和原始文件视图。技术实例恢复旧配置，原评论和切换后新增评论均可读取。12 张表的结构一致，旧行逐行仍存在，没有恢复数据库快照覆盖新数据。
6. 清理此演练项目的容器。随后按准确 Compose 项目标签查询，剩余容器为空。技术目录、诊断镜像和证据保留。

完整机器结果见 `compose-results.json`。前后正式 app/nginx 的容器 ID、镜像 ID、启动时间和运行状态完全一致；没有修改正式 3000/64401、正式库或主仓。没有输出 Docker 环境值或读取、复制正式密钥。技术环境仅使用本机镜像默认值与合成值，未调用模型。

## 结论边界

这是隔离 Docker 机制和修后真实构建入口的验证，不是正式发布脚本从准备到恢复的端到端验收，也不代表最终候选全部验证完成。正式切换仍需根协调器准备最终包、取得用户确认并依已审顺序执行一次正式验收。

网络方面，成功构建日志仍显示 BuildKit 将本地标签正规化为 `docker.io/library/...`，但元数据步骤立即完成，没有失败版本中的鉴权或镜像拉取步骤。构建使用 `--pull=false --network=none`，源码校验容器使用 `--network none`；本次没有抓包，因此不宣称构建进程绝对未发送任何网络数据包。

修正只涉及基础镜像标签固定和构建入口，本次没有重复已通过的 Compose 全流程。演练过程中未修改发布脚本或产品源码；脚本修改由另一代理完成并独立审查。
