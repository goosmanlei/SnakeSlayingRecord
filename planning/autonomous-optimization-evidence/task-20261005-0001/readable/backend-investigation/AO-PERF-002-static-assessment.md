# AO-PERF-002 静态评估：出口按出现位置复制，可行但尚未验证收益

**结论：存在一项范围较小的方案，值得先做隔离试验，不宜直接作为已完成优化交付。** 可以把内容展开拆成“内部按内容键构建共享子树”和“每次公开返回时生成独立JSON树”。关键是第二步必须按每个位置创建字典和列表；不能把现有逐层复制直接换成一次 `copy.deepcopy`。本评估只读取源码和已有证据，没有实现、测试或性能采样。

## 为什么标准 deepcopy 不满足边界

集中内容用相同校验值代表相同子树，一个节点可能被多个父节点或同一列表的两个位置引用，这构成有向无环图（DAG）。若内部让两个位置指向同一列表，标准 `deepcopy` 的 `memo` 会记住已复制对象，从而在新结果里仍让两处指向同一个新列表。随后修改第一处就会改变第二处；这与“两个位置可独立修改的JSON投影”冲突。

安全出口需要针对JSON的递归树复制：遇到字典或列表，每次访问都新建容器并继续递归；不可变标量直接返回；不按对象身份去重，不使用共享 memo。因此两个位置即使来自同一个内部子树，也得到两个独立容器。代价至少与最终输出树大小成正比，这是为了正确返回完整独立数据所必需，不能再用引用共用偷偷省掉。

## 最小变更方案

保留 `expand(store, key, visiting=None, cache=None)` 的签名及原有作用域取缓存方式，新增两个私有步骤：

1. 内部展开函数继续按键查现有缓存、检查缺失和 SHA、解析节点、检查重复对象键和环，并递归取得子节点。递归期间不深复制已完成子树，只有完整成功的节点才进入缓存；异常仍在 `finally` 退出 visiting 集合。
2. 公开 `expand` 对内部完成结果执行一次上述JSON树复制，再返回给调用方。缓存命中也经过同一个出口复制。`hydrate`、自定义 resolver、row factory 的AO-PERF-001字符串复用、原始排版复原和最终归档校验保持原样。

这里“内部只读”是所有内部消费者不修改缓存容器的约定，并不是Python把字典/列表冻结了。最小方案沿用显式 `cache` 参数存放普通JSON值的现有形式，避免再引入冻结节点类、标签元组或一套新序列化模型。默认production范围和两处显式自有缓存（归档active reader、迁移archive_cache）都只创建、传递和清理缓存，源码未见修改其中节点；若要求连拿到显式cache的内部调用方也绝不可能改节点，则必须引入真正不可变的节点表示，改动和兼容范围明显扩大，**本轮不建议做这种重构**。

原来的 `copy.deepcopy` 不能保留在内部缓存命中处，否则热点仍在；也不能只给顶层dict/list浅复制，否则下一层容器仍共享。自定义树复制只处理JSON的dict/list和标量，不需要接受任意Python对象。当前字段来自 `json.loads`，但 `archive_recipe`、压缩recipe及`value`内的合法嵌套JSON也要走相同出口，不能误当成只有字符串。

## 风险与最小验证边界

- **重复子树别名。** 同一子节点在数组两处、两个不同对象字段、不同深度及两个独立expand返回值都要分别可变；修改任意深层列表/字典不能串到另一位置或缓存。这是本方案的主要正确性风险。
- **异常缓存。** 成功的共享子节点可保留，但失败的父节点不能入缓存；首次/重复缺失、损坏SHA、非法节点、重复对象键和环仍失败，访问后读范围及visiting清理完整。
- **显式缓存契约。** 不能让默认production缓存与归档自有cache混用，也不能把冻结元组暴露给现有JSON调用方。当前cache是内部参数；若后续发现外部调用依赖其中对象身份或就地修改，则应停止该最小方案并重新判断兼容范围。
- **原始排版与resolver。** `hydrate(resolve=...)` 不改；压缩recipe重复token、新旧archive recipe、嵌套JSON、数字写法、Unicode转义及最终字节校验继续由现有回归验证，不能只比较解析后的JSON。
- **复杂度和内存。** 理论上减少同一子树在每一层构建时的重复复制，也可能减少缓存内部重复容器；出口仍需完整物化。这个推断不等于运行收益，可能被SQLite点查、JSON解析/序列化和大响应传输抵消。

## 是否值得推进

基线独立profile中，李寄实体的deepcopy累计约413/991毫秒，material_entries约316/918毫秒；这是AO-PERF-001之前、带profiler开销的调用链定位，不能直接当作新候选可节省时间。001之后李寄完整HTTP收益仍未证实，说明进一步检查复制成本有理由；同时，接口返回约16.4MB完整历史，复制变快也未必使实际页面明显变快。

建议只把“内部不复制＋出口无memo树复制”作为一项有明确撤回条件的候选：首先在独立工作区验证上述别名与准确原件边界，再用同一原始数据比较AO-PERF-001与001+002，而不是只与旧基线比，分别测李寄、素材列表和逐镜的完整HTTP、CPU和RSS。若新增收益没有超出波动，或需要新冻结节点体系/大量迁移兼容代码，撤回002，保留001和已测证据。当前不建议为002扩大功能、缩减完整历史或引入跨请求缓存。
