## 已定位的共同成本

`material_entries` 是素材列表、实体索引和逐镜页面共用的条目聚合。未启 profiler 的三个只读样本为 964.5、608.5、656.9 ms；首个新连接样本偏慢，保留而不混成稳定提升依据。独立 cProfile 中，总耗时 917.7 ms，其中 row factory 的 `hydrate` 累计 572 ms、内容树 `expand` 492 ms、`deepcopy` 316 ms。这些包含调用链的累计时间，不能相加。SQL trace 与计时分别运行；共 32,847 条 SQL，其中 15,147 次内容节点点查、6,705 次历史轮次查找、4,114 次别名查找。

S001 的 cProfile 总耗时 1,215 ms，其中共用 `material_entries` 899 ms；李寄实体总耗时 991 ms，其中内容树展开 657 ms，深复制累计 413 ms。profile 本身增加开销，以上用于定位占比，最终收益只能用正常 HTTP 和真实页面 A/B。S001、李寄实体和组合历史索引的所有诊断模式返回的规范化 JSON SHA 与同一路 HTTP 一致；内部 `material_entries` 没有独立 HTTP 端点，其三个模式 SHA 彼此一致。准确初版详情的三个模式 SHA 彼此一致，本轮没有为该具体详情另加 HTTP 样本。

## 推荐的一项窄改动

在 `material_storage.row_factory` 中，**只在既有 `_production_reads` 读取范围内**，用完整物理 payload 字符串作键，复用 `hydrate` 返回的不可变 JSON 字符串。`material_entries` 先读取当前需求，再由素材身份聚合重新读取这些需求；本次观测到 4,142 次 `hydrate`，约为 2,088 个需求的两轮读取。现有内容节点缓存避免再次点查数据库，却仍会反复深复制树、重新拼装并序列化相同 payload。字符串复用可直接针对这段重复工作。

该方案不缓存当前对象头或完整响应，不改 `expand` 的可变对象返回规则，也不影响直接调用 `hydrate(resolve=...)` 的自定义解析。每次 `record_view` 继续独立 `json.loads` 构造投影，因此对展示字段的修改不应串到另一份记录；完整物理字符串包含准确引用，旧修订和新修订自然区分，读取范围退出/异常后立即释放。它随后形成 AO-PERF-001 候选；具体已测收益与未证实项见对照摘要，不从本轮基线推定固定提升。

必须验证同一范围两次读取内容相等但可变投影相互独立；同一原始内容在重复子节点及不同历史修订中不交叉污染；下一请求可见新需求/新评论/采用，异常后复用和事务释放；自定义 resolver、损坏内容检查、导出/空实例恢复继续正确。完整 HTTP 响应 SHA 与基线逐路径比较，页面另由根代理真实操作。

## 内存对照方式

请求内文本复用可能以更多常驻字符串换 CPU，必须独立测峰值常驻内存。`db_diagnostics.py` 后续版本增加 `resource.getrusage(RUSAGE_SELF).ru_maxrss`：macOS 原生单位是 bytes，报告统一 bytes；分别在读取完成和 JSON 序列化后记录峰值。它是整个进程生命周期的峰值，不是某次操作净分配；因此 A/B 每个端点各启动独立子进程、`--mode timing --repeat 1`，保持相同只读快照、Python、输出步骤和原始环境，至少五对交替顺序，不把同进程递增高水位当独立样本。

`window2` 诊断先于 RSS 字段加入，没有原始 RSS，不能追补推算。795 次 HTTP 也未改变中途口径。后续获得根代理另分配的窗口后，已完成五对独立进程内存对照；新原始证据与读取、序列化峰值单列于对照摘要，不回填旧窗口。
