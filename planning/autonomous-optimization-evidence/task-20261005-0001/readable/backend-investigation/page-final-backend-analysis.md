# 最终页面与后台请求对照

本轮浏览器负载下，评论读取的后台耗时改善得到再次确认；C2 系统管理页没有重现旧批次约 53 ms 的变慢方向。**C2 的页面差额仍小于样本波动，不能据此承诺稳定的页面提速比例。** 制作页面的大幅差异主要对应各自材料、实体、场景和就绪检查接口，不能全部归给评论优化。

本分析只读取根代理已经完成的四阶段记录，未启动服务、浏览器、HTTP、数据库查询或新测量。独立页面统计者同期自行复算，本报告未使用其结论。全部逐请求匹配、原值、统计及回执保存在 `page-final-backend-analysis.json`。

## 输入与关联方法

A 为 `b874b959af9c918a482e8488dc25cb0204ab5772`，B 为 `3b20d609448365103ebcf381776e33869913fe8b`，顺序 A1/B1/A2/B2。四个服务回执的开始—结束 UTC 分别为 08:16:17—08:20:04、08:20:05—08:22:34、08:22:34—08:24:56、08:24:57—08:27:20。各阶段均以 SIGTERM 退出，`error=null`、`identity_unchanged=true`，没有末尾检查错误；本分析再次比较首尾 identity，四组均相等。同一 A/B 的产品树摘要也分别相同。

四阶段数据库 SHA 均为 `5c6d00ee6efa7506201bbef46ffd69bde49f7300c4697fe66036e87ace7ed4f0`，实例文件名称/大小/mtime 摘要均为 `88954d509dafa087c2216042cf72a31e5e73ed7e62568c474b38d47194e119ca`。后者不是全媒体字节复验。浏览器记录为 Chrome 154、1440×900、DPR 1，原 probe SHA 保持。端口及进程清理采用根的独立回执；本只读分析没有再次查询端口。

每阶段恰有 70 个根文档 GET，与 70 个浏览器 `time_origin` 按时间排序后，完整 URL 一一吻合。随后在相邻根导航之间按 GET URL 和出现次序关联 fetch，核对浏览器 headers 时间与服务秒级日志落在同一约 1 秒范围内。共 280 个页面、2,540 个 fetch GET 全部成功关联，均为 200 且 handler 无异常；各文件原断言全部为真。JSON 中保留服务日志行号、完整路径和时间差，关联错误为零。

这是独占窗口中的顺序/URL 约束关联，不是 request-id 链路追踪；日志只有秒级时间，不能据此重建精确服务排队起止。图片请求可以跨越导航，其所在日志段只能确定时间上下文，不能机械归属给当前文档。每阶段另有一次 GET instance/POST comments 的只读预检，未计入 fetch 性能；POST 均为预期 405。A1 首次使用默认代理的 GET 返回 502 且没有进入服务日志，原预检记录保留为已排除失败。

## 必须分开的四种时间

`server_elapsed_ms` 是 handler 入口到响应写出结束的墙钟耗时，包含执行、文件读取及可能的写出等待，**不是纯 CPU 时间**；不含接收前排队、浏览器连接调度以及停止计时后的日志格式化/落盘。

浏览器 `headers_ms - start_ms` 是发起 fetch 到拿到响应头的等待。页面启动同时发起八个请求，服务则单线程顺序处理，因此多个 fetch 的等待高度重叠，不能相加。`ResourceTiming.responseEnd` 才表示该资源网络正文接收结束，也不等于 JSON 解析完成。原 probe 只记录全局 `pendingBodies` 和 `last_network_at_ms`，没有逐请求解析完成时刻；本报告不补造该时刻。

页面 `scenario_ready_ms` 从导航起点到正确内容的语义采样结束，另有 180 ms 稳定确认不计入该值。每个样本可以连续划分为“导航到首个 fetch”“首 fetch 到最后一个 fetch 网络正文完成”“之后到语义就绪”；这三段同一条时间线可相加。分段中位数不可直接相加，串行 handler 总和也不能与浏览器重叠等待相加。

例如 `C2-B2-0.json`：八个启动 fetch 在约 0.3 ms 内发出，最后一个 summaries 请求从发起到响应头等了 145.6 ms，而其 handler 只有 0.322 ms；framework 等了 63.8 ms，而 handler 为 0.120 ms。八项浏览器等头时间相加是 676.4 ms，实际从首 fetch 到最后网络正文仅 145.4 ms，说明直接相加会重复计算队列等待。该样本从导航到首 fetch 168.2 ms，之后网络区间 145.4 ms，再到语义就绪 24.7 ms，合计 338.3 ms。23 个脚本/CSS/探针的 handler 总和仅 9.14 ms，不能把浏览器前 168.2 ms 都写成服务端工作。

## 图片断连和未覆盖范围

整窗日志不是零错误：A1/B1/A2/B2 分别有 5/9/13/5 条 `BrokenPipeError`，共 32 条，均为 D2 连续刷新附近的 `/api/production/files/*.png`。它们集中在新文档开始的同一个秒级时间桶，当前文档的 ResourceTiming 没有同路径条目。这与旧文档图片在刷新时取消相符，但缺少网络请求 ID，**仍只能作为取消/排队残留的解释，不能精确证明每条所属旧导航**。

日志 `status=400` 是错误路径最后一次尝试 `send_response` 的值：产品 `_file` 先发 200，写图片遇到 `OSError` 后错误处理再尝试 JSON 400，后者也可能断管。因此不能说浏览器实际收到了 32 份 400 JSON。对应原行号、路径和时间桶全部保留，没有删除失败。

2,540 个被 probe 拦截的 fetch 仍全部成功；但图片原生加载不在 fetch 错误断言内，动态图片解码也不是探针就绪门槛。因此 D2 内容就绪测量可以按原有口径报告，不能同时宣称这些样本证明“全部图片均传输成功或解码完成”。真实媒体验收及原件完整性须引用各自证据。原件没有因本分析被修改或重新生成。

本报告提供后台与页面时间的证据联系及边界；页面收益是否超过波动、剩余回退是否可解释，继续采用独立页面复核结果，并保留这里指出的配置成本、媒体取消和单次 navigate 样本局限。
