# 项目指令运行开销调查与优化实施

任务：`task-20261017-0001`。用户希望查清本项目任务运行慢是否与指令有关，并明确要求实施优化计划。本次执行使用 **gpt-6-astra／max**，只修改故事仓的项目指令、上下文、任务发布方法及直接关联指南。

**项目指令确实带来了可避免的读取和补读负担，已完成对应优化；现有证据不足以认定它是整项任务耗时的主因。** 三份默认入口的UTF-8正文总量从125,878字节减到33,795字节，减少73.2%。这是入口阅读量的变化，不是任务提速73.2%；没有取得可隔离模型、工具和人工等待的同条件端到端耗时。

## 查到了什么

### 入口会怎样进入上下文

本机Codex CLI为0.163.0。以同一工作区、同一提示、显式Astra/max运行 `codex debug prompt-input`，修改前后都能取得完整项目 `AGENTS.md`；`KNOWLEDGE.md`、`STATE.md`只有名称和链接，正文没有自动注入。它们随后因项目“进入先读三份文件”的要求，被Agent主动读取。

修改前合并的全局与项目指令正文为24,550字节，本机 `project_doc_max_bytes=65536`，没有发现项目规则被自动截断。此次缩减的是默认上下文和主动读取量，并未修改全局配置或上限。官方也将AGENTS描述为按目录发现并组装的指令链；本机实际渲染用于核对当前环境，而非仅按官方默认值推断。[OpenAI：AGENTS.md加载规则](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

项目中“读到链接就继续读”的风险来自入口之间重复引导，而非工具自动递归抓取。现在明确：已有同版指令直接使用，链接按当前问题选择；输入缺失或版本不符时仍回到准确来源补齐。该方向也符合官方针对Astra提出的按任务读取、避免无关文档前置的建议；官方建议不能替代本项目的验证。[OpenAI：Astra的Skill与指令设计](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

| 优先级与问题 | 实施位置及结果 | 预期减少的负担 | 保留条件与验证 |

| P1：同版材料和多个账本入口反复读取 | AGENTS明确复用已读未变内容；[任务发布SKILL](../skills/task-definition-publish/SKILL.md)先按摘要、状态和范围定位，再读相关任务完整目标／结果 | 避免整本账本和旧材料重复输出 | 不按标题去重；相关目标、授权、依赖与结果仍要完整核对，认证要求不减少 |

## 交付、回退与核验

本次普通do授权本地实现、提交和受管集成；不新增远端推送义务。准确候选与本地main交付状态由本任务账本的Git回执和验证结果记录；用户核验前不调用 `_complete`。已运行的旧会话可能仍带有原注入内容，修改不会自动删除其会话历史；新会话使用新入口，旧任务按正常恢复核对有效规则即可，无需为此重启共享服务。

需要恢复某条遗漏知识时，先从上述基线及原权威正文定位，补回确有作用的事实／入口并沿同任务提交；不把整份旧STATE覆盖到已前进主干。若恢复较大范围，按实际冲突逐项处理，保全其他任务的新状态与残留。

用户可从项目根查看AGENTS“跨会话恢复”、KNOWLEDGE两张任务导航表及STATE当前制作／残留部分：应能找到当前任务与准确制作入口，且不会被要求先重读全部历史验收。报告中的优化计划已落实到这些文件；之后自然任务若仍有明显延迟，可沿其真实工具记录继续定位具体阶段，本次不承诺未经测量的时间收益。

本机证据在本任务worktree `.runtime/task-20261017-0001/`：`evidence.json`保存基线、前后哈希、查询与会话证据，`prompt-before.json`／`prompt-after.json`保留准确本机渲染，检查和交付回执供用户核验。只保留核验／恢复所需资料，核验用途结束后由本任务收尾维护受管退役；分支和Git报告继续保留。临时资料清理的实际数量与路径回读见同目录 `cleanup.json`，不对其他任务执行清理。
