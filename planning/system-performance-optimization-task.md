## 任务目标

1. 在 1008—1010 三个依赖完成并集成后，以准确代码版本和隔离数据快照建立基线，整体排查相关共用请求、数据读取、响应体、资源加载与前端渲染，定位等待原因；不把历史优化报告的耗时当成本轮基线；复核下节判断是否仍适用于三个依赖完成后的实现。
2. 优化全部五组问题、十二类操作：制作拆解的加载／切集／切场／切镜；实体管理的加载；素材管理的加载／筛选；镜头制作的加载／切集／切场／切镜；各入口实体大卡的打开。首开、重复访问及快速连续操作均在范围内，保留准确内容和阅读上下文。
3. 优先评估按需加载、目录与正文分离、可重建列表摘要及数据库筛选分页、媒体与 API 服务分离和有界请求并发；随后评估准确修订及编号缓存、浏览器缓存、缩略图与按需媒体加载，最后依据慢查询和实际读写竞争优化 SQLite。逐方向给出采用或不采用的实测证据。
4. 从系统整体读写链路评估缓存设计，比较现有请求内复用、跨请求缓存及其他瓶颈优化的收益、一致性成本和维护成本，形成明确取舍，再实施必要优化。若需要缓存，统一设计缓存对象、层次、准确键、依赖、容量、失效和恢复规则，覆盖前台操作及后台导入／发布；按实际部署处理跨进程可见性、并发更新与重复加载。缓存属于可选手段，不能以命中率代替用户等待改善，不能因缓存混淆实例、筛选、对象、修订、版本或候选。
5. 第一阶段保留 SQLite 和现有原件存储；本任务可在隔离实例验证必要摘要表、索引与 WAL，正式数据库变更随最终候选明确提交审阅。仅在持续写入争用或明确多实例／多人共享需求成立时提出 PostgreSQL 迁移方案；Redis 和对象存储同样按实测收益与维护成本评估，不默认引入。新增外部服务、存储迁移或费用另定范围。
6. 交付可复现的前后性能证据、正确性与真实浏览器回归、双仓候选及必要发布／恢复步骤，遵循本文全部验收口径。沿项目流程办理最终确认与串行交付，并清理失效过程资源。

## 现状判断与实施顺序

2026-10-07 对正式容器只读核对：正式库为主项目 `.runtime/review.sqlite3`，原件在本地文件系统，SQLite 日志模式为 `DELETE`；正式 `server.py`、`store.py`、`ui_projection.py`、`static/app.js` 与当时同级系统源码 SHA-256 一致，实际 Nginx 配置与源码一致。核对时系统配置引用 `ae65eef5248283d399f6c9f722afd1d71c669979`。以下是代码行为及候选优化判断，未重新测量耗时，不能作为瓶颈占比或提速证据；执行时以依赖完成后的准确版本重新核验。实现路径以系统仓库根为基准。

| 顺序 | 当前代码行为 | 候选方案及预期收益 |
|---|---|---|
| 第一批：入口加载 | `review_desk/static/app.js` 的 `init()` 等待九个接口完成，包含资料、评论、结构、剧本及编号 | 先读取当前页必要内容，其他模块进入时加载；目录与正文分离，减少无关请求对首开及刷新的拖累 |
| 第一批：列表读取 | `review_desk/ui_projection.py` 先汇总素材、历史候选、关联和数量，再筛选分页；分组路径返回完整筛选结果 | 可重建列表摘要保存标题、归属、预览和数量，数据库完成筛选、计数、分页，当前页批量读取、详情按需读取，兼容 1010 最终分组及分页行为 |
| 第一批：请求调度 | `review_desk/server.py` 使用单线程 `HTTPServer` 和共享 Store，媒体经 `_file()`；Nginx 全部请求代理到 Python | 静态资源和真实媒体交给 Nginx；API 使用有界并发及独立连接，减少媒体与接口互相等待 |
| 第二批：重复计算 | 多数 GET 经 `review_desk/business_codes.py` 的 `annotate()` 读取映射、遍历返回值；已有复用主要局限于请求内 | 按准确修订缓存不可变解析及编号，批量读取关联；设容量与清退边界，改善重复打开和版本切换 |
| 第二批：资源加载 | 文件和 JSON 响应统一 `no-store` | 不可变原件、带版本静态资源允许缓存，动态数据按版本校验；列表缩略图与按需加载减少传输和解码，放大、下载及采用仍使用原件 |
| 第三批：数据库 | 活库使用 `DELETE` 日志模式，尚未重新测量慢 SQL 或锁竞争 | 从查询计划及等待证据决定索引、批量查询、短事务；有实际并发需求时评估 WAL，不承诺普遍提速 |

列表摘要是可重建查询数据，不可变修订、准确历史、评论、采纳／采用及原件继续作为权威。采用摘要时梳理所有前台写入与后台导入／发布入口，优先同事务维护；不能同事务时用版本校验及可靠回退防止过期读取。完整统计、分组显示项数与唯一素材数保持原口径，不能以少读当前动作所需内容制造收益。

并发须有上限，每个执行单元独立连接，保持读快照、事务及版本冲突检查。Store 初始化含表结构及迁移逻辑，不能逐请求重复执行迁移；不得跨请求共享可变缓存。CPU 密集的 Python 展开仍须减少工作量，增加线程本身不保证加速。归档引用须安全解析或物化为真实字节，不能把引用文件直接作为媒体发送；保持文件校验、路径边界和 Range 分段播放，物化产物明确清退。

缓存按实例、准确对象／修订和筛选组合隔离，容量有上限；可变的当前头、评论及采用覆盖写后失效，跨进程按实际部署验证。HTTP 缓存身份与实际字节一致，错误、冲突及结果未知不能缓存为成功。派生缩略图不替代原件，媒体加载与正文可用分别计时。

WAL 指 SQLite 预写日志模式，可改善部分读写并发，但仍只有一个写入者。评估时核对 SQLite 版本及已知缺陷、Docker 挂载的锁和共享内存语义、检查点与长期读事务，同步适配一致性备份、旁路文件、隔离恢复和发布／回退；不能复制正在写入的单个库文件作为完整备份，也不能以未披露的持久性降低换取提速。

先优化读取范围和调度。仅当持续写入争用或明确多实例／多人共享需求成立时提出 PostgreSQL 迁移；它仍需列表摘要和按需读取。Redis、对象存储按共享缓存或媒体分发需求与运维收益取舍，不默认添加基础设施。

技术机制参考：[Python HTTP 服务](https://docs.python.org/3/library/http.server.html)、[SQLite WAL](https://www.sqlite.org/wal.html)、[Nginx 文件发送](https://nginx.org/en/docs/http/ngx_http_core_module.html#sendfile)。这些资料解释机制，不是本系统性能测量证据。

## 可验证完成标准

1. **依赖和覆盖。** 三个前置任务完成且准确交付已纳入基线；逐项记录五组十二类操作的复现对象、操作、预期结果、瓶颈、改动和证据。素材筛选覆盖已有类型、搜索、集场、采纳等实际可用条件及其组合；大卡覆盖不同页面入口和不同实体规模。无法复现的项明确条件和结果，不冒称已修复。
2. **可比较的测量。** 在相同数据、机器、浏览器、视口和缓存条件下，至少做两轮交替的基线／候选对照，每轮每侧每条被测路径至少十个有效样本。首次读取与重复访问分开，记录具体清理／预热范围，不把刷新当成全冷启动。保留原始样本、中位数、波动、请求数与体积、相关接口耗时及 CPU／内存代价。
3. **真实且逐项的收益。** 主要计时从用户动作开始，到目标内容正确显示且必要控件可用结束；媒体实际加载／可播放另列，工具往返耗时不作页面耗时。每条已复现慢路径在两轮对照中的中位耗时均下降，且每轮降幅超过该轮前后样本四分位距的较大值；其余关键路径出现同口径回退须解决。四分位距是中间 50% 样本的耗时跨度，此规则用于排除波动，不代表长期性能保证。不以只加缓存、单次变快、空壳先出现或后台提速替代页面收益；未达项保持未完成并说明原因。
4. **全局缓存设计与数据正确性。** 交付系统读写链路、候选方案比较及选型依据；采用缓存时列出对象／键／依赖、容量与清退规则，以及每类写入对应的失效范围和一致性保证。验证首次未命中、重复命中、相关写入后失效、历史准确读取、并发写入和迟到响应、跨实例隔离、容量上限及失效后的重新读取；按实际部署验证跨进程可见性和并发重复加载，重启后不能依赖残留旧值才能正确工作。覆盖前台评论／采纳／参考选定及后台导入／发布等实际写入入口。不采用缓存时，给出系统级评估结论、瓶颈与替代优化证据，不强造缓存设施。
5. **真实交互无回归。** 在实际可用浏览器中验证四页加载、集场镜切换、素材筛选／分页、大卡多层打开返回、媒体预览、准确历史／版本／候选、关系图、评论及采纳。桌面与窄屏保持 1008—1010 的最终行为；快速连续切换不闪回旧结果，写后界面正确更新，筛选、页码、滚动与草稿不因优化意外丢失。相关自动检查通过；浏览器受阻项单列未验证，不能由接口或静态检查替代。
6. **交付和收尾。** 交付逐路径前后对照、准确双仓候选、必要配置与操作说明，以及缓存启停／清空或其他变更的恢复方案；保全业务原件、准确引用、评论与采纳／采用历史。隔离测试数据不进入正式库，正式应用与集成按项目最终候选确认流程串行进行。清理报告给出实际删除范围和数量、回读结果、保留用途及移除条件；未处理项说明原因和下一步。

7. **读取范围、摘要与候选取舍。** 六个方向逐项记录适用性、瓶颈证据、取舍及结果；首次进入、筛选分页、详情打开和评论保存覆盖服务端等待、响应传输与浏览器渲染。评论保存用于正确性及回退检查，不扩展创作功能。列表记录查询量、展开次数、响应体和处理代价，验证分组、页边界、组合筛选、总数、焦点和准确历史；采用摘要时与权威记录全量核对，验证所有实际写入入口、完整重建、中断及独立恢复。
8. **并发、媒体与存储变更。** 采用并发时验证单窗口多请求、多窗口、媒体播放同时读写及快速切换，记录上限、连接生命周期、锁等待与总内存。媒体直接服务或物化后核对原件字节、Range、缓存身份及路径边界；索引、摘要表或 WAL 具备迁移、备份、重建／恢复及回退步骤，隔离验证后纳入最终候选审阅。重启、缓存首次未命中和相关写入后仍正确；不把历史未证实的写入收益宣称为本轮改善。

### 测量和正确性细则

- 初始 Notebook 没有指定绝对毫秒目标或固定提速比例；执行中的 300 毫秒补充见本文开头。本任务保留已确认的重复测量与波动判据，不承诺固定加速比例。四分位数采用同一种固定算法并记录，不能为使结果通过而改变口径或事后筛除慢样本。
- 一轮基线／候选对照分别使用同一冻结快照的独立副本，至少两轮按基线、候选、基线、候选顺序测量；缓存命中条件、失败／超时样本及实际选中对象留证，样本不足不报告可信尾延迟。基线和候选间的功能差异须能解释，不能删内容、缩减结果集、延后当前动作的必要数据或降低媒体质量来制造改善；不相关模块及非当前页内容可按需读取，派生预览与原件加载分别计时。
- 大卡的计时终点必须包含当前实体与所选状态／素材的必要正文和可操作控件；关系图及媒体若分阶段呈现，分别记录可用时间。记录新开、关闭后重开、另一实体和准确历史目标，不只测同一个对象的缓存热路径。
- 既有优化仅有请求内数据复用等历史实现事实，是否仍适合本轮由准确基线验证。若引入跨请求缓存，须梳理全部受影响读写入口，不以固定过期时间掩盖“写后仍显示旧评论／旧采纳／旧参考”的问题；失败、冲突和结果未知不能被误缓存为成功状态。
- 共享性能测量窗口由本任务统一安排，不与其他负载测试或浏览器自动化竞争。当前正式库与服务仅按明确发布流程操作，测试评论、采纳、导入及失效测试都在隔离实例进行；本任务不包含新媒体生成或作品改写。
