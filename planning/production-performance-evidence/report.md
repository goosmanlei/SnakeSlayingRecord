# 生产制作页面性能诊断

2026-10-20。目标是解释“进入页面慢、交互卡、CPU 占用高”，并给出可执行的优化顺序。本轮为诊断，未修改正式代码、配置和业务数据，未发布或执行优化任务。

当前已测实两处主要服务端开销：媒体路径逐请求执行的删除记录检查，在同库隔离单次 profile 中耗 278ms CPU；成片审阅的字层读取校验占该请求 profile 累计耗时约 91%。VPS 未命中缓存的实体目录一次等待 16.45 秒。四页都有可优化项，但不能把所有等待都归为浏览器渲染，也不能据代码中的 observer 推断存在持续循环。已有 OSS、缩略图、波形预计算、分页和读取缓存应保留，并针对未覆盖的路径补齐。

- 后端 profile 在同一正式 Python 3.12.15 容器中运行，代码不变，数据、配置、缓存全部指向一次性私有备份；正式源 SQLite 以 `mode=ro` 备份，profile 禁止网络。只复制 19 份字层 JSON、47,654 字节，未下载原件。各路径仅 profile 一次，存在采样器开销和副本缓存差异；profile 用于归因，不作为改造后的收益。约 951MB 私有实例已按准确路径清理，保留脚本、pstats、摘要及清理回执。

从时间线“画面”轨道打开 ASH002 大卡，卡片接口首包 1938ms，后续准确素材详情 7.6ms；11.53 秒观察窗主线程累计 260.4ms。播放该镜头 720p 视频的 11.54 秒窗口内，主线程工作 290.3ms，渲染进程 CPU 计数增加约 760.8ms；此短样本的渲染主线程未持续忙碌，但该计数不包括全部 GPU/系统视频解码进程。播放后已恢复暂停。

该大卡暂停后的 55.75 秒观察窗内，主线程累计工作 32.8ms，布局和样式重算次数均为 0。上述静止场景未复现持续高 CPU，当前已测实的是读取期间的服务端 CPU 热点，不能将两者混称。

## 优先处理的路径

### 1. 媒体跳转前的历史删除记录查询

所有生产媒体请求在 `review_desk/server.py:670` 调用 `candidate_reset.erased_files()`，然后才走 OSS。`candidate_reset.py:19` 对 `production_current_operations.result` 执行 JSON 格式筛选并读取匹配的回执。媒体路径绕过一般制作读取作用域，因此该函数在一次页面的不同图片请求间没有结果复用。

隔离实测该函数一次耗时 **278.6ms、CPU 278.4ms**，不包含 HTTP、OSS、签名或 Store 初始化。执行计划为全表扫描：7,796 条操作结果合计 334,098,751 个字符，却只需要 1 条 4,467,763 字符的删除回执，最终得到 962 个已删除文件。约 93.3% profile self 时间落在 SQL 游标迭代与 JSON 筛选，Python 对命中回执的解析约 14ms。这为本机 300 多毫秒跳转等待提供了直接解释。[原始摘要](backend-profile/erased-files-summary.json)

应把“某个准确文件是否已删除”变成轻量可索引查询，或按删除回执的事务版本缓存删除集合；不能简单删除这道检查，否则已删除原件可能重新可访问。优化验收要分别记录应用 307 耗时、OSS 首包耗时和整页图片出现时间，避免把云端延迟与应用 CPU 混成一个数字。

### 2. 成片审阅逐字幕重复读取和校验整份来源

前端 `static/editing.js:71` 用 POST 读取审阅数据，绕过一般 GET 读取缓存。`editing_review.py:308` 逐元素 `verify_binding()`，每条字层进入 `text_layer_document()`，重复读取 JSON、校验整个工程、遍历来源并处理提交快照。

第一集最新成片有 116 个元素，其中 66 条字层记录（59 条字幕、7 条标题）对应 19 个不同字层素材，工程有 22 个来源。应在一次一致读取内，按准确素材修订和组件身份共享字层文档、工程校验和来源结果，各条字幕只做自身条目的检查。保留当前归属、精确版本和评论定位校验。优先做请求内复用，再决定是否需要长期结果缓存。

隔离 profile 一次耗时 **3.469 秒、CPU 2.851 秒**，116 个元素全部可用。其中 `text_layer_document` 实际调用 66 次，累计 **3.153 秒，占请求约 90.9%**；来源提交处理 `submission` 1,750 次，记录读取 1,927 次，SQL SELECT 11,215 次。[原始摘要](backend-profile/summary.json)

同一 profile 还发现 `resources.settings()` 调用 **264 次**、累计 **1.132 秒，占约 32.6%**：每次重新读取并解析 742,587 字节的 `instance.json`，仅此文件的逻辑读取累计约 196MB。这里与字层开销嵌套，两个百分比不能相加；逻辑读取也不等于实际磁盘物理读。应把资源配置所需的小字段从大实例配置分离，或按配置文件物理版本缓存已验证结果，并保证配置更新与凭据轮换按约定及时生效。

### 3. 参考候选摘要不应为了列候选而读取所有原件

`reference_candidates.py:24` 为每个候选的原件调用 `asset_path()`；经 `production_media.py:105` 进入 OSS `materialize()`。缓存缺失时会下载整个原件；暖缓存也会完整读取文件计算 SHA256。前端在参考列表接近视口时即加载候选，不需要用户真正播放或选中所有候选。

当前一个李寄手部素材的 4 个唯一原件合计 59.2MB；青蓬演唱音色的 14 个候选对应 21 个唯一原件、47.9MB。这是代码可能处理的去重原件体积，不是本次实测下载量。应让候选摘要使用准确资源目录中的大小、类型、状态与版本，预览按需读取派生；制作、导出及正式完整性验证继续校验准确原件。

### 4. 局部读取仍进行全剧聚合与父节点重复反查

`production_scope.py:10` 指定局部范围后仍遍历 17 集、42 场、416 镜。单镜实体入口在 `production_breakdown.py:55` 先后构建两次 graph，部分旧管理目录随后被覆盖。`ui_projection.py:420` 为场内每镜构建 workspace，又经 `entity_contract.py:203`、`audiovisual.py:133` 反查父场／父集；正式库执行计划显示父节点查询扫描 revisions，当前共有 19,586 条。

应分离轻目录与当前范围的详细用途投影，在同一次请求内共享准确父子关系和 graph。场 reader 已知集场链时直接传递，独立开卡仍校验准确组成。类型查询缺索引也是候选，但应先在副本验证最小索引与查询改写，避免泛加索引。

这类工作主要改善首次进入、切换范围以及写入后的缓存失效。现有暖缓存命中会直接返回最终字节，不能把冷构建问题解释成每次都慢。

## 已经具备、不应重复建设的能力

当前已有 OSS 精确版本直读、小图与大卡图片派生、服务端波形预计算、素材 DOM 分页、镜头详情延迟读取和批次限制、最终 HTTP 字节缓存、Graphviz Worker、4 个服务线程与 8 个排队连接。

资源目录记录的 small 图中位数约 9.1KB、large 图约 49.4KB、波形 JSON 约 12.6KB；波形最多 1600 个峰值，浏览器没有完整 WAV 解码流程。签名已有 300 秒进程内复用，资源目录也有文件版本缓存。后续应先处理上述绕过优化的路径，不直接升级硬件、增加线程、再建一套缩略图或迁移媒体存储。

## 建议实施顺序与验收

先修媒体跳转、成片审阅与资源配置的重复读取，其次修参考候选摘要与局部数据投影，再合并大卡评论重绘、收窄缓存失效，最后处理拖选、关系图和组件销毁。每阶段都用当前准确数据做前后对照，避免把多个改动叠加后无法归因。VPS 需核对并发布准确候选后另测首次和重复读取，不能以本机通过代替远端通过。

验收至少分开记录：缓存命中、首次构建、正常评论写入后读取；应用接口等待、服务器 CPU 时间与字节读写、OSS 网络等待；浏览器主线程/Worker、静止/播放/拖动场景。正常评论写入场景应在隔离实例验证，本轮没有为测量写正式评论。

建议优化目标（尚未实现、需正式任务确认测试条件）：本机暖态小图签名响应中位数低于 50ms；最新成片审阅低于 500ms；局部切换常用接口 P95 低于 500ms；一次手势不重复全页评论重绘；无播放时静止页面无持续轮询/布局；多轮开关大卡后监听器和内存不持续增长。准确版本、原件完整性、删除保护、评论草稿与阅读位置必须同时通过功能回归。

本轮没有测全剧最大关系图、长时间媒体播放/解码、弱网、多用户并发或完整浏览器堆快照，不能把这些未测项宣布正常，也不能承诺未经对照的百分比收益。
