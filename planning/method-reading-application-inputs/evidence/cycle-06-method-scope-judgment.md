# 方法阅读改进与本机阶段回读的范围判断

建议分别承担两个完整目标：**作者能准确保存、回读和恢复本次创作；人能读懂方法、提出改进并明确用于后续工作。** 两者处在同一工作链，但不是同一根因，不宜合成“重做方法系统”。本机回读是已阻碍真实实践的确定缺口，可先修；方法阅读可同时用真实正文验证页面样例。两者完成后用一次隔离创作串联，避免各自只验接口。

本判断复用了根会话已完成的页面实践，没有重做UI调查。核对基线为主仓 `6a14c238d7fb344fc12cf284be68a11d6bc0a409`、配套desk `123e7d00912414d4ca1241a03ad5e91ee9d18622`。以下系统路径以 `../story-review-desk/` 为基准；其余路径以故事项目根为基准。

## 为什么分开，而不按文件或仓库拆任务

ASH010 的 `understanding` 原文共711字符，通用工具登记成功后回读只有摘要。这源于制作当前稿压缩后，作者工具仍把服务回执当全文：`scripts/creative_method.py:51–73` 没保存阶段原始产物；`scripts/media_method.py:61–81` 的draft同样依赖调用者自己保留输入文件。后端 `review_desk/production_current_methods.py:9,29–38` 对六类制作工作只留摘要，是已确认的存储边界，不应回滚。

人的另一段困难是：正文被原始编辑框和配置字段包围，方法与准确共用章节缺少可读、可评论的连续路径；保存方法和选用方法又分属两张表单。这发生在 `static/methods.js:17–42,94–105` 及方法正文评论投影，不由阶段压缩引起。即使阶段原文恢复可读，人仍面对同一配置表；即使方法页变得易读，作者的 `read` 仍只得到哈希。

两段已有稳定连接点：`methods.resolve/prepare` 已将准确绑定、方法文件、适用共用章节和作品输入交给新步骤；旧步骤按原包恢复（`review_desk/methods.py:261–324`）。因此分开仍各自解决完整问题，不需要增加任务间数据实体或先重构公共服务。

## 作者侧：恢复现有步骤目录应有的能力

可复用现有 `delivery.json`、方法/资料文件、准确输入和 `stage-*.json` 回执。`scripts/method_runtime.py:52–92` 已能按原内容交付文件、补齐中断交付，拒绝内容变化及越界路径；`methods.artifact()` 已按执行与阶段幂等登记、校验前置阶段、拒绝用摘要伪造新产物（`review_desk/methods.py:377–408`）。无需让服务重新存制作草稿全文。

必要补齐的是：登记时在本步骤目录保留实际原始产物，并将它与准确执行、阶段、服务回执绑定；回读时返回这个原文或结构化产物，校验服务摘要，恢复不借当前方法重建旧稿。字符串和JSON对象都要无损。摘要中的 `output.sha256` 才是原始产物摘要；回执外层 `output_sha256` 校验的是压缩后的输出，不能混用。保存原文、请求已成功而回执未落盘、请求结果未知等中断，应沿原执行和阶段恢复，不重复创建业务步骤。旧包有完整远端输出时继续可读；只有摘要且本地原文确已缺失时明确报缺，不从当前作品补写。

完整范围是当前压缩契约的六类工作：视听设计、素材判断、字层、生成准备、结果审阅、媒体方案。修共用作者交付能力并覆盖 `creative_method.py` 与 `media_method.py` 即可；不能将小说、剧本、读者等未压缩入口误报为丢稿，也不迁回旧制作版本树。媒体begin的输入和finish的定稿包已有保留能力，修的是阶段草稿与回读／恢复衔接，不能笼统宣称整个媒体工具没存正文。

验收以本轮ASH010样例和一份真实结构的媒体方案为主：新步骤保存后由工具实际读回正文；关闭进程再恢复仍为相同方法、输入及产物；不同正文、错误归属、缺文件明确失败；服务成功但本机未收完整回执能据原身份恢复；远端仍只留约定摘要。其余压缩工作类型验证同一契约，旧完整输出入口做兼容对照。只读源码和现有单测通过不能代替这次CLI链路。阶段产物仍是本机过程资料，随恢复用途结束清理，公开作品导出不带走私有草稿。

## 人的入口：读方法、提出意见、明确用于后续工作

可复用准确 `GUIDANCE` 方法/资源对象、当前绑定、`GET /api/methods` 和准确记录读取；目录已经返回绑定引用到的准确旧修订，不必再建一套方法目录（`review_desk/methods.py:44–80`）。复用根已实读的视频手册目录、段落、表格和媒体表达，以及现有评论和回应机制；保持原工作位置。普通阅读直接呈现正文和有必要的用途，不以折叠大量内部字段作为简化。

仍需真实实现两件事。第一，从方法准确修订的 `files` 派生可定位正文，让意见固定到相应文件、段落及原摘录。当前 `store.validate_target()` 只认识 `blocks/body` 或特定制作文本，方法的 `files` 不能直接锚定；全局评论也未允许此类GUIDANCE（`review_desk/store.py:593–631`）。所以不是加评论按钮即可。共用章节必须读方法所引用的准确修订；来自项目Markdown的只读投影，继续由唯一源文件维护和同步，不能在配置页另存可改副本（`review_desk/methods.py:247–248,276–287`）。

第二，建议把“保存并用于后续视听设计”作为一项明确动作，保存准确方法并更新用户选定的既有绑定，呈现真实生效范围。当前保存只改一种对象、以 `expected_version` 防并发覆盖（`:226–258`），不会自动更新绑定。可以组合既有保存能力，但必须处理方法已保存而绑定更新失败的情况，不能报“已用于后续工作”；其他工作类型和旧执行保持原选择。稳定标识、阶段名、原始条件JSON等由系统保留校验，普通改正文不要求人重新配置。需要维护执行契约的既有能力继续可达，不把它复制为另一套配置模型。

验收先用隔离方法9／绑定8的实际条款：从方法读到所引共用章节再返回原位置；提出准确意见并回查原摘录；改稿并明确应用到所选后续工作，重新取得步骤包证明使用准确新正文；恢复旧步骤仍为方法8。并发冲突、保存待用或应用失败均说清实际状态，不静默改其他绑定。另从项目源文件维护的共用资料验证只读和准确版本评论；原评论、旧方法包、资源内链及空实例恢复保持。该任务不包含作者草稿全文存储，不展示作者执行日志，也不新增审批或效果看板。
