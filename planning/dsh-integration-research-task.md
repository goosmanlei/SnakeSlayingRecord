## 报告需要回答的问题

1. **当前能力和落点。** 将实际创作与审阅链条映射到两套系统：故事与场镜结构、实体/状态/关系、素材需求当前方案、准确参考与候选、原件、评论修订、方法文件历史及执行快照、作者阶段保存与恢复、模型/媒体调用和正式发布。逐项区分 DSH 已有通用能力、本系统必须保留的业务语义、连接层工作和没有证据的能力；给出可定位到提交与文件/符号的依据。
2. **三条可比较路线。** 至少比较：保留现有系统、只连接 DSH 执行能力；以 DSH 插件/应用入口统一工作体验并复用必要现有后端；将业务能力和界面整体迁入 DSH。比较各自能完成的同一工作、复用范围、侵入性、部署复杂度、升级耦合、用户体验与退出成本；如果某路线被当前架构明确限制，指出准确限制和替代方式，而不是假定接口存在。
3. **推荐架构。** 明确 DSH、领域服务/适配层、现有 Python 作者工具与审阅台、存储和前端各承担什么；现有代码保留、包装与重写分别列明。解释 DSH 插件和配置如何组成、工具/API/SDK 如何交接、业务数据和会话记录谁是权威、方法与准确输入如何固定、原件如何引用、长任务如何恢复，以及人工评论如何进入下一次修订。会话日志不自动替代业务历史，通用附件不自动等价于素材候选。用一张组件关系图和一条关键流程时序说明设计，不仅画抽象分层。
4. **成本拆分。** 分别估算最小可验证接入、可日常使用版本与整体迁移的开发人日区间，覆盖后端/插件、界面、现有工具适配、数据与历史迁移、验证、发布恢复和长期维护。说明角色/熟悉程度、复用比例、范围、依赖和估算依据，区分工程工作量与多人日历工期，给出主要不确定性、范围敏感项及避免重复计数的汇总。代码规模只是辅助证据，不用行数机械换算工期。另列模型/媒体、存储和运行资源等持续成本驱动；没有实测或现价依据就给公式、假设或未知，不虚构费用节约和性能收益。
5. **渐进落地与可退出性。** 给出推荐先做的最小闭环、阶段产物、进入下一阶段的验收门槛、哪些改动可独立推进、何时才需要迁移数据，以及失败时如何继续现有工作。明确 DSH 快速迭代与稳定前 API 对维护成本的影响、版本适配责任和后续需要验证的少数关键问题。建议足以用于决定是否另立实施任务，本任务不自动派发实施工作。

至少用两个本系统具体工作场景检验推荐方案，例如“读取准确镜头/素材输入及方法，准备当前方案，再由人审阅结果”和“人对准确对象留下意见，AI 修订、回读保存并继续后续工作”。说明现有路径、目标路径、数据/方法身份、正常对照、交接结果和返回上下文；同时走查中断后恢复、过期输入或并发修改、重复回调/结果未知中的相关故障情形，写清拒绝、查询和继续的位置。这里只要求有依据的设计走查；没有实际执行就标明推演，不承诺已经验证故障恢复。
