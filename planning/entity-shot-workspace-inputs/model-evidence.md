# 镜头统一工作区与素材方案：模型证据

本记录用于定义优化任务，不是实现或独立产品验收。2026-10-11 读取主仓 `a1fb15c`、审阅台 `a8914dc` 与正式库 `.runtime/review.sqlite3`；数据库仅用 SQLite `mode=ro` 查询，未初始化 Store、未写业务数据。以下源码路径以故事仓根目录为基准。浏览器现场由根会话另行记录。

## 1. 镜头应只有一个身份，进入实体的共同工作区

当前有 134 个 ENTITY（人物51、道具63、歌曲4、空间16）、344个 AV_SHOT、65个 AV_SCENE、17个 AV_EPISODE。镜头还不是 ENTITY。实体大卡通过 `ui_projection.py:183` 进入实体审阅；镜头则在 `:234–239` 单独构造 `position_review`。`generation.py:95–119` 的实体范围与 `:163` 起的实体快照，也将镜头排除在共同所有者逻辑外。只把“打开完整镜头”按钮换一个名称，不能满足此次统一目标。

建议在任务中明确：镜头成为统一实体模型的 shot 子类型，沿用原稳定对象 ID 与 ASH 编号；实体管理、关系图、大卡和视听编排均引用同一个镜头对象。不得另建 ENTITY 镜像与 AV_SHOT 双写。底层兼容读取可以保留迁移适配，但不能形成第二份业务正文或第二套编辑入口。视听场对镜头的有序组成仍是编排关系，不能因实体化丢失集场与镜序。

既有镜头内容需要整体承接：叙事目的、准确剧本出处、时长/帧率、出场人物道具与适用状态、连续性背景，以及所需素材。普通实体大卡和视听页共同使用“基础信息＋素材分组 Tab／列表＋右侧当前方案与历史候选”的组件及选择状态，不能维持两套外观相似、行为不同的镜头详情。

迁移规模：344镜拥有1115个 REQUIREMENT（素材需求），其中主机位344、反机位72、首帧344、视频344、字层交接11。镜头 `products` 只有699项，不能仅按 products 迁移而丢掉416个机位需求。镜头内还有351个 `key_states`，它们是局部关键状态，不是现有280个 STATE 对象；应保留描述、素材对应关系和作品语义，在新的基础信息及分组中承接，不为套用人物状态模型强制复制成351个完整状态实体。

例：ASH001 的稳定 ID 为 `av-e01-a01-s01`。其 `before-singing` 描述的是歌本尚在手中、河石尚在篮面，为摊本、压石后开唱留出动作空间；对应首帧素材需求。其叙事目的则是认识靠唱歌谋生且熟悉街坊的女孩，并为老汉接唱的玩笑建立期待。两个内容有不同价值，统一卡片不能只保留标题或把关键状态改成空模板。

现有28条统一关系以镜头为直接端点，4897条关系以镜头为使用上下文。`business_relations.py:49–58` 用一对稳定对象 ID 生成关系身份；保留镜头 ID 可避免平白重建关系。适用范围、素材引用与出场构成不应自动复制为多套关系。

必要消费者包括：

- `../story-review-desk/review_desk/audiovisual.py:9–10,26–124,132–170`：集场镜类型、组成、故事来源、关键状态与产物校验。
- `../story-review-desk/review_desk/production.py:363–394`、`generation.py:95–119`、`ui_projection.py:180–248`：实体/状态校验、共同所有者范围、卡片路由。
- `../story-review-desk/review_desk/production_breakdown.py`、`business_relations.py`、`production_current_bundle.py`：用途定位、关系、当前稿导出恢复。
- 故事仓 `scripts/audiovisual_materials.py`、`audiovisual_publication.py`、`audiovisual_reading.py`、`verify_video_inputs.py`、`exact_text_handoffs.py`：仍直接消费 AV_SHOT，不能只改审阅台而令下次发布重建旧模型。

验收须核对迁移前后镜头身份、集场顺序、1115个素材归属、351个状态描述、699个产物关联及实际关系端点／上下文；同时回查旧镜头链接、素材链接、评论及导出恢复。故事至剧本不改，历史提交快照不改。

## 2. 当前方案已只引用素材；历史调用展示仍混入文字依据

正式库1549个素材需求的当前 `generation.inputs` 共3817项：REQUIREMENT 3471项、ASSET 346项，ENTITY及STATE为0。当前 `generation.reference_links` 与 `generation.prompt_links` 也都是0。`generation.py:62` 已限制方案输入为 ASSET 或 REQUIREMENT。因此不能把此次问题定性为“所有当前方案正在上传实体状态”。

历史提交快照不同：`production_submissions.input_contents` 中存在ENTITY 306项、STATE 328项、INPUT_LOCK 6项、ASSET 290项；其中12个ENTITY及11个STATE内容已是不可用收据。`production_current.py:422–455` 原样投影历史请求，`static/material-review.js:130–153` 又把非媒体输入标为“实体”“状态”“剧本依据”“文字依据”，对应根会话看到的旧候选界面。

取舍：生成参考区只呈真实素材，小卡双列；实体、状态和剧本是创作依据，不应再次作为“文字依据”列表挤回生成参考区。必要约束留在当前基础信息、故事出处及已有 Prompt 的实际语义中。旧提交快照保存原始事实，不能为清爽界面把历史记录改写为“从未存在文字依据”，也不能把已删实体版本替换为今天的实体内容。

例如 ASH001 视频当前方案中的音频输入为阿蘅音色的准确原件片段（0–5.6秒）；Prompt 已明确它只提供声音身份，实际表演按本镜重演。人物状态来源和关系说明不能被照搬成更多输入卡，也不能因清理参考列表删掉这类有效生成约束。

Prompt 展示应使用可点击的 `@素材名字`，点击与小卡对应同一素材／候选。现有 `static/production-breakdown.js:282–312` 按“图片1／音频1”等输入槽建立链接。新显示名称必须绑定稳定输入身份，不能靠全局替换名字；同名素材、重复引用、准确音频区间、输入顺序及评论选文锚点仍须正确。历史实际 Prompt 字节及快照哈希保持不变，展示名不是改写历史调用；后续提交仍按模型要求生成正确槽位映射。

## 3. “始终有当前方案”需要补齐17个旧素材，不能只改 Tab

`production_current.py:397–419` 只有素材身份本身是 REQUIREMENT 时才返回当前 plan。正式库有17个素材仍用 ASSET 作为素材身份，各有1个候选；按当前投影，这些身份本身不返回 plan。它们包括旧角色对白、李寄造型、歌曲派生片段；6个有模型生成请求，11个是编辑产物。不能把没有模型 Prompt 的剪辑产物伪造成模型生成。

根会话实例 M003 即 `asset-liji-voice-01`（李寄对白声线候选），没有 REQUIREMENT alias。其候选1的操作为 `call-liji-voice-01`，快照 `requirements=[]`，但 request 保存完整 `seed-audio-1.0` 参数和216字 Prompt。两个旧 inputs 是制作输入锁及实体文字依据，没有媒体输入；实体输入内容是“此准确版本已删除”的收据。其音频原件、候选身份、字幕及时间范围应原样保留。

当前方案初始化规则已获根会话采纳：

1. 已有当前方案原样保留，不被旧候选覆盖。
2. 没有当前方案时，从该素材最新真实候选中语义无歧义的可用内容初始化可修改当前稿；复制真实工具、模型、参数、Prompt及可确认的媒体引用，保持媒体角色、裁切、时间范围和顺序。历史请求的非媒体依据不进入新的生成输入列表，旧事实仍保存在原快照。
3. 编辑或导入产物保留真实制作方式和已有操作事实，不捏造模型、Prompt、参考或执行能力。没有足够依据的字段留待编写，当前方案入口仍存在；未完整的方案不得悄悄提交生成。当前稿与历史候选在视觉和语义上明显区隔。
4. 候选选择只是查看历史；把历史方案复用到当前须是明确操作，不能浏览候选便覆盖当前稿。初始化不得触发付费生成。

M003应复用其确切对白 Prompt 作为当前稿的有用起点，而非无意义空壳；但不能自动并入 `material-voice-li-ji`。后者是另一素材需求“李寄·音色参考”，已有当前计划，试样文字为“我把东西放在桌上，等你说完再走”，与M003的作品对白用途不同。以同属李寄或都为音频推断同一素材，会破坏创作目标。

验收使用M003（有候选、原无当前稿）、M2597（有当前稿、无候选）、现有同时有方案与候选的素材，以及一个编辑派生音频。确认始终有当前稿入口、候选仍可读看听、复制不改历史、切换不改当前稿，并回查17个旧素材无遗漏。未实际观看或试听的内容，此记录不作质量结论。
