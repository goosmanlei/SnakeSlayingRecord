优先级 P2，复杂度“复杂”，按当前任务策略采用 `gpt-6.1-sol / xhigh`。不与其他任务同时执行：任务涉及全站子路径、数据重置、共享 Nginx 接入及远端正式切换，采用单项执行以便统一核验；共享服务写入与两仓集成仍按项目规则串行。当前只发布任务，不执行本任务目标。

3. 每次显式发布整体替换本体验实例的应用、业务库、素材、页面内容和派生缓存。上轮新增评论、采纳、选择、配置变更及其他体验修改不承诺保留，不做双向同步和增量合并。
4. “不保留历史版本”指 VPS 上旧的部署版本和上轮体验数据。当前发布快照自带的作品、素材版本、准确引用与有效历史按本机完整数据保留，不再次执行业务历史清理，也不重写 Git 历史。
5. 浏览器草稿、页面状态与缓存须按环境及发布身份隔离，发版后不让旧草稿、旧对象选择或旧客户端资源混入新数据；普通刷新、重启与正常使用仍保持现有交互。页面只给出必要的体验提示：“体验环境，操作将在下次发布时重置”，不加入内部日志或任务追踪面板。
6. AI 润色等现有外部 API 功能需要体验环境自己的服务端凭据与已授权额度，并核验出网条件。凭据不进入业务导出、浏览器、Git 或公开发布包；不得未经授权充值、购买或放开无限调用。未配置凭据时不能把禁用功能、模拟结果或仅验证错误提示称为完整体验验收通过。缺少凭据或额度时先完成独立工作，最终准确列出阻断；真实 API 调用和费用不会因重置数据库而撤销。

## 已核实的环境与资源依据

以下均为 2026-10-08 本会话的只读观察，用于解释方案，不代表扩容后的状态或执行时仍然有效。连接目标始终从用户当时的 `~/.ssh/config` 中解析 `vps`，不将历史 IP 写死为部署目标。

| 项目 | 当时观察 | 实际含义 |
| --- | --- | --- |
| 远端系统 | Ubuntu 22.04.5，x86_64，2 vCPU | 应构建与执行时目标架构匹配的 Linux 镜像；当时本机应用镜像是 arm64，不能直接据此推断远端兼容 |
| CPU | 负载约 0.06；15 秒被动观察平均忙碌 4.39% | 当时 CPU 有余量，不代表代理高峰或后续浏览器负载 |
| 内存 | 总计约 1.57 GiB，可用约 605–628 MiB，无 swap | 原规格的主要瓶颈；用户后续扩容，执行时重查 |
| 磁盘 | 根盘约 40 GiB，剩余约 16 GiB | 当时足够当前数据及有限发布暂存；视频增长后重新估算 |
| 既有服务 | Xray 常驻约 34 MiB；Nginx 容器约 9 MiB | 保护既有代理与网站，不因上线体验版停止或重建它们 |

当时 Docker 支持 cgroup v2、CPU 和内存及 swap 限制。内核累计有过一次内存不足终止计数，但系统日志读取权限不足，时间和原因未查明，不归因于 Xray 或审阅台。

当时本机正式 SQLite 约 110 MiB；数据库、导出、素材、页面内容和读取缓存合计约 1 GiB，不包含系统、Docker 镜像、Git 历史、任务工作区或备份。本机低负载应用容器约 92 MiB、Nginx 约 16 MiB；此前较大数据集的原生 Python 并发演练峰值 RSS 约 524 MiB，见 [production/system-performance/results.md](../production/system-performance/results.md)，不是 VPS 实测，也不是整个宿主机内存。

讨论中的 2 vCPU、4 GB 内存、约 60 GB SSD、20 Mbps 出网是容量建议，用户没有确认采购该规格。约 1 vCPU、640–768 MiB 应用上限及 1–2 GiB swap 也是扩容前的试运行建议，不应硬编码为最终配额；新增 swap 属于主机配置变更，需另有授权。实际资源预算依据扩容后的余量、最新数据及有上限的真实验证确定。保留完整功能并清除旧部署主要减少磁盘与维护成本，不会显著消除运行内存需求。无需 GPU；图像、声音及视频模型推理仍由既有外部平台承担。

## 部署结构和路径适配

复用 VPS 已存在的 Nginx 容器、域名及 HTTPS，只新增一个审阅台应用容器，通过 Docker 内网反向代理。SQLite 与受管素材持久化在目标实例下，前台正常操作仅写体验库。现阶段不引入 Redis、独立数据库服务器、消息队列、集群或本机模型推理服务。

当时已核实：Nginx 容器名为 `nginx.me.leiguoguo`，镜像为 `nginx:alpine`，网络为 `nginxmeleiguoguo_default`；宿主 `~/www` 只读挂载到 `/usr/share/nginx/html`，80/443 已发布。配置和证书目录位于远端 `~/my-config/nginx.me.leiguoguo/`；当时 `nginx -T` 通过，站点根目录开启目录浏览，虽挂载 htpasswd 文件但没有生效的 `auth_basic` 指令。执行时回读实际配置与容器身份，不按旧名称盲改。

- 整个 `/lijizhanshe/` 路径先建立访问保护及完整反代规则，再放置数据库或私有实例文件，避免既有静态根目录将它们公开下载。认证方案复用现有 Nginx 能力，凭据交付与持久配置独立管理，未经授权不通过聊天公开密码。
- `/lijizhanshe` 规范跳转到 `/lijizhanshe/`。前端 API、脚本样式、图标、图片音视频、方法页附件、下载、深链、刷新及浏览器前进后退均支持该前缀，不占用域名根部 `/api` 或 `/static`。同时回归本机根路径部署，不能只用正文字符串替换掩盖遗漏。
- 保留媒体 Range、ETag、压缩、准确原件及内容哈希行为；数据缓存只是可重建派生物，发版后按新发布身份重建。当前 SQLite 日志模式与缓存的选择以执行时已验证的系统契约为准，不为 VPS 迁移顺带启用未经验证的 WAL。
- 配置明确使用远端根目录和公共入口，排除本机专用证书挂载、绝对用户路径和开发入口。目标实例不得依赖任务 worktree 存续；不要把 `.codex-task`、完整 `.runtime`、本机密钥、调试数据或任务副本一起上传。
- Nginx 仅在校验通过后做必要的平滑重载，不修改其他站点、Xray 或共享 Docker 网络的用途；应用端口不额外暴露公网。

## 全量发布与故障处理

1. 以执行或恢复时的两仓最新有效主干和准确正式数据为基线；任务发布时的提交、旧性能快照和两个前置任务各自完成时的旧提交均不是永久固定基线。主仓 `config/instance.json.review_desk_commit` 与系统交付提交保持准确一致。不能用可能过期的 `export/` 冒充本机当前活库。
2. 在隔离工作区用一致性备份或当前完整导出恢复能力准备完整可运行数据，并校验新空实例、引用、原件哈希和数据摘要。本机完成与目标架构匹配的镜像构建和必要验证，尽量避免在小 VPS 上全量恢复大型 JSON、构建镜像、跑测试或转码。发布包只包括运行必需文件，并保存足够小的准确提交、哈希和发布身份信息。
3. 远端先核对真实路径、符号链接、已有文件、空间、容器与挂载、当前发布身份及并发发布者。发布锁只控制本体验实例。上传到受保护暂存目录并校验完整性；失败或中断先查询是否已切换，不重复执行未知副作用。
4. 阻止新的体验写入并等待在途写入结束，短暂停止本体验应用，整体切换代码、数据库和素材后启动检查。切换窗口内可以临时保留旧目录和准确旧镜像用于失败恢复，但不让新旧实例并行写同一数据库，也不直接覆盖运行中的 SQLite 文件。
5. 新版启动、数据和真实页面检查通过后删除上轮体验库、旧专用部署目录、旧专用应用镜像及本次无用暂存／缓存，长期只保留当前体验版本。新包损坏、上传失败或启动失败时保留必要恢复现场，并给出准确恢复入口；失败现场不等于永久保留全部历史。
6. 仅清理本体验实例归属明确的资源。共享 Nginx、Xray、其他站点、共用镜像层、用户会话及本机正式 current/previous/base 约定不纳入此处“不保留历史”的删除范围。禁止全局 Docker prune 或针对整个 `~/www` 的全量删除。记录实际清理范围和保留理由。
